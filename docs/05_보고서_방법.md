## 1. 베이스 에이전트 분석

### 1.1 출처

- 교수님이 슬랙에 올린 `all_total_vue_student.zip` 을 `src/` 에 옮겼다 (`src/BASE_ORIGIN.md`).
- 이식 커밋 `55e15f1` 은 원본과 바이트 단위로 같다. 이후 `src/agent/`, `src/server.py`, `src/mcp_server.py`, `src/data/` 는 바뀌지 않았다 (`git diff 55e15f1 HEAD` 로 확인).
- 개선 코드는 `src/ext/` 와 `src/adapter.py` 에만 있다.

### 1.2 파이프라인 (실제 구현)

`src/agent/graph.py` 의 `build_graph` (310-338줄) 구조는 아래와 같다.

```
route ─ chat ───────────────────────────────→ chat_answer → 종료
      └ incident → plan → gate → research → replan_check → analysis → write → validate → finalize
                                    ↑              │                    ↑          │
                                    └─ 런북 없음 ──┘ (보충 조사 1회)     └─ 불합격 ─┘
```

| 노드 | 하는 일 | 모델 | 위치 |
|---|---|---|---|
| route | incident / chat 분류 | fast | graph.py:76 |
| plan | MCP Prompt 절차를 읽고 시스템별 모니터링 task 생성 | fast | graph.py:102 |
| gate | `needs_analysis=False` 면 analysis task를 코드로 제거 | 없음 | graph.py:123 |
| research | 모니터링 Tool과 런북 Resource 병렬 호출. task당 0.35초 고정 지연 | 없음 | graph.py:138, 161 |
| replan_check | 수집물에 런북이 없으면 런북 task 1개를 추가하고 research로 되돌림 | 없음 | graph.py:217 |
| analysis | analysis task가 남아 있을 때만 실행 | fast | graph.py:234 |
| write | 수집된 사실로 답변 작성 | quality | graph.py:255 |
| validate | 규칙 검사. 불합격이면 write로 되돌림 | 없음 | graph.py:275 |

plan이 만드는 research task는 전부 `kind=monitoring` 이다 (`openai_llm.py:160`). 런북 조회 task는 `replan_check` 에서만 생긴다. 어떤 런북을 쓸지는 이 노드 한 곳에서 정해진다.

### 1.3 구조적 공백 3가지

**(a) 런북을 질의가 아니라 모니터링 알림 키워드로 고른다.**

- `_classify_incident_type` (graph.py:205-213) 은 수집된 모니터링 결과의 `status` 와 `alerts` 문자열만 본다. 사용자 질의는 입력에 없다.
- 규칙은 `_INCIDENT_TYPE_RULES` (graph.py:192-202) 의 순서대로 `in` 검사를 하고 처음 맞는 것을 쓴다. 순서는 latency, pool, cpu, memory, heap, timeout, network, disk, down 이다.
- 여러 시스템을 조사하면 알림 문자열이 하나로 합쳐지고, 시스템 순서가 아니라 규칙 순서가 결과를 정한다. 예를 들어 payments-service(알림에 `CPU`)와 gateway-service(알림에 `timeout`)가 함께 조사되면 `cpu` 규칙이 `timeout` 규칙보다 앞서므로 cpu-spike가 고른다. 이 예는 코드에서 추론한 것이며 실측 결과가 아니다.
- 런북은 1개만 가져온다 (gap task 1개, graph.py:225-226). 복합 장애에서 두 번째 런북은 구조상 들어올 수 없다.
- 맞는 키워드가 없으면 `db-down` 으로 폴백한다 (graph.py:213). `monitoring.json` 의 알림 문구에는 `down` 이 들어간 것이 없다. db-down은 폴백으로만 도달한다.
- 질의는 간접적으로만 영향을 준다. plan이 질의에서 시스템명을 찾고, 못 찾으면 auth-service로 폴백한다 (graph.py:47, openai_llm.py:52, 62).

**(b) Validator가 규칙 기반이다.**

- 합격 조건은 `len(draft) >= 30 and "1)" in draft` 한 줄이다 (graph.py:279).
- 3번째 시도에서는 불합격이어도 통과 처리한다 (graph.py:281). 즉 최대 3회 작성한다.
- 불합격 피드백은 항상 "응답이 너무 짧습니다" 문구다 (graph.py:283-285). 내용의 관련성, 근거 정합성, 요청 형식은 보지 않는다.

**(c) 모델 분리가 이미 되어 있다.**

- 기본값은 fast = `gpt-4o-mini`, quality = `gpt-4o` 다 (server.py:52-55).
- route, plan, analyze는 fast (graph.py:78, 113, 243), write는 quality (graph.py:263) 를 쓴다.
- 처음 계획한 "모델 티어링"은 베이스에 이미 있었다 (`docs/00_개선계획.md` 일정, PROGRESS 10:05 기록). 그래서 비용 축을 새로 정의했다. 정의는 2.4, 2.5절에 있다.

### 1.4 이식 시 원본과 달라진 점

base 구성도 `adapter.py` 가 만든 LLM 객체를 쓴다. 원본 `OpenAIFastLLM`/`OpenAIQualityLLM` 을 상속해 `_chat` 만 바꾼 것이다 (meter.py:107-130).

| 항목 | 원본 | 평가용 |
|---|---|---|
| 요청 payload (모델, 메시지, temperature 0, JSON 모드) | 같음 | 같음 |
| 사용량 기록 | `total_tokens` 합계 × 가상 단가 | 입력/출력 토큰을 나눠 Meter에 기록 |
| 재시도 | 없음 | 429/5xx/타임아웃 시 최대 4회, 지수 백오프 (meter.py:86-104) |
| HTTP 타임아웃 | 120초 (openai_llm.py:98) | 60초 (meter.py:91) |

그래프 자체는 원본 `build_graph` 를 그대로 호출한다 (adapter.py:119).

## 2. 개선 설계

### 2.1 원칙

- 원본 노드 함수를 지우거나 고치지 않는다. `build_graph_ext` 가 원본 노드를 import해서 쓰고, 플래그에 따라 노드 3개만 바꾼다 (graph_ext.py:21-24, 131-134). 엣지와 조건 분기는 원본과 같다.
- `adapter.py:97-101` 의 `_is_base` 가 참이면 `src/ext` 를 거치지 않고 원본 `build_graph` 를 부른다.
- 개선은 누적으로 켠다. `rag` → `rag_judge` → `rag_judge_cost` 순이다. RAG 없이 Judge만 켠 구성은 없다.

### 2.2 플래그와 교체 노드

| config 플래그 | 교체 노드 | 바뀌는 것 | 원본이 남은 곳 |
|---|---|---|---|
| `runbook_selection: rag` | replan_check → `replan_check_rag_node` (graph_ext.py:45) | 알림 키워드 규칙 → 질의 임베딩 유사도 순위 | `replan_check_node`, `_classify_incident_type` (graph.py:205, 217). base가 그대로 사용 |
| `validator: judge` | validate → `validate_judge_node` (graph_ext.py:77) | 규칙 검사 → LLM Judge 4지표 | `validate_node` (graph.py:275) |
| `cost.model_tiering: true` | write → `write_cascade_node` (graph_ext.py:66) | 1차 초안을 저가 모델로 작성 | `write_node` (graph.py:255). 캐스케이드 노드가 내부에서 그대로 호출 |
| `cost.cache: true` | 노드 교체 없음. fast LLM 래퍼와 retriever에 캐시 부착 | route, plan, 질의 임베딩 재사용 | 캐시가 꺼지면 원래 호출 경로 |

### 2.3 RAG 런북 선택 (`src/ext/rag.py`)

- 런북 6개 파일 전문을 `text-embedding-3-small` 로 임베딩해 색인한다. 색인은 프로세스당 1회이고 `.cache/` 에 디스크 캐시한다 (rag.py:92-99).
- 질의 문장을 같은 모델로 임베딩하고 코사인 유사도로 순위를 매긴다. 벡터는 단위 길이로 정규화해 내적을 쓴다 (rag.py:101-110).
- 순위는 상위 `top_k=3` 을 남긴다. Recall@k, MRR 계산 대상이다.
- write에 넣을 런북(투입 런북)은 별도 규칙으로 고른다. 1위 점수에서 0.05 이내인 것만 넣는다 (`select_feed`, rag.py:113-117). 복합 장애면 2개가 들어갈 수 있게 한 장치다.
- `margin=0.05` 는 측정 결과를 보기 전에 정했고 이후 조정하지 않았다 (rag.py 모듈 주석, rag.yaml 주석).
- 런북이 이미 수집됐거나 보충 조사를 1회 했으면 원본과 같이 통과시킨다 (graph_ext.py:48-52). 바뀐 것은 보충할 런북을 고르는 방식뿐이다.
- 오프라인 테스트용 `LocalNgramEmbedder` 가 있으나 실측에는 쓰지 않는다 (rag.py:59-61).

### 2.4 LLM-as-a-Judge Validator (`src/ext/judge.py`, `graph_ext.py:77-115`)

- 4지표: relevance, completeness, domain_appropriateness, clarity. 한 번의 호출에서 지표별 Pass/Fail과 사유를 받는다.
- 점수는 Pass 개수 / 4 이고 임계치는 0.75 다. 3개 이상 Pass하면 합격이다.
- 불합격이면 실패한 지표의 사유를 피드백으로 붙여 write로 되돌린다.
- 무한 루프 가드: 재작성 2회 또는 시작 후 120초 중 먼저 닿는 조건에서 멈추고 통과 처리한다 (graph_ext.py:94-103). 가드 발동은 `judge_history` 에 기록한다.
- 시간은 Judge 호출이 끝난 뒤에만 검사한다. API 지연이 길어지는 경우를 위해 질의당 하드 상한 300초를 `asyncio.wait_for` 로 따로 둔다 (adapter.py:52, 132). 넘으면 오류로 기록한다.
- 파이프라인 Judge 모델은 `gpt-4o-mini` 다 (rag_judge*.yaml).
- 파이프라인 Judge가 JSON을 읽지 못하면 4지표를 모두 Fail로 처리한다 (ext/judge.py:68-73). 재작성 쪽으로 기우는 보수적 처리다. 평가용 Judge의 처리는 3.4절에 있다.

### 2.5 비용 최적화: 캐스케이드와 캐시

캐스케이드 writer (`write_cascade_node`, graph_ext.py:66-74)

- 1차 초안은 `gpt-4o-mini` 가 쓴다. Judge가 반려하면 2차부터 원래 write 모델 `gpt-4o` 가 쓴다.
- 프롬프트는 같고 모델만 다르다. 이벤트에 writer 모델 이름을 남긴다.
- 반려가 잦으면 호출 수가 base보다 늘 수 있다. 저가 모델 초안, Judge 호출, 고가 모델 재작성이 모두 붙기 때문이다.

질의 캐시 (`QueryCache`, meter.py:135-161)

| 항목 | 내용 |
|---|---|
| 키 | 질의를 소문자로 바꾸고 공백과 `. , ! ? ~, …` 를 하나의 공백으로 접은 문자열 |
| 저장 대상 | route 결과, plan 결과, 질의 임베딩 벡터 |
| 저장하지 않는 것 | 모니터링 결과, 런북 본문, 답변, Judge 판정 |
| TTL | 600초 (`cache_ttl`) |
| 수명 | 프로세스 동안, 구성 이름별 (adapter.py:55-61) |
| 적중 시 | route, plan은 API를 부르지 않고 사용량 0으로 기록 (meter.py:164). 임베딩은 호출을 생략 |

- 모니터링 값이 호출마다 달라지므로 research와 write는 캐시하지 않는다.
- 의미가 같은 다른 문장은 같은 키가 아니다. plan 키에는 MCP 절차 프롬프트가 들어가지 않는다.

## 3. 평가 설계

### 3.1 4개 구성

| 구성 | 런북 선택 | Validator | write 모델 | 캐시 |
|---|---|---|---|---|
| base | 키워드 규칙 | 규칙 | gpt-4o | 꺼짐 |
| rag | RAG | 규칙 | gpt-4o | 꺼짐 |
| rag_judge | RAG | Judge (gpt-4o-mini) | gpt-4o | 꺼짐 |
| rag_judge_cost | RAG | Judge (gpt-4o-mini) | 1차 gpt-4o-mini, 반려 시 gpt-4o | 켜짐 (TTL 600초) |

- 공통: route, plan, analyze는 `gpt-4o-mini`. temperature 0. 같은 평가셋 24건. 구성당 1회 실행.
- 인접한 두 구성의 차이가 그 단계의 기여다. rag − base는 RAG, rag_judge − rag는 Judge, rag_judge_cost − rag_judge는 비용 최적화다.
- 구성 정의는 `eval/configs/*.yaml` 이고 실행 순서는 `run_ablation.py:31` 의 `ORDER` 다.

### 3.2 평가셋 (`eval/queries.yaml`, version 2)

| 카테고리 | 건수 | 정답 런북 | 보는 것 |
|---|---|---|---|
| normal | 12 | 1개 | 런북 6종 × 2건. 정상 경로 |
| constrained | 3 | 1개 | 길이, 표, 줄 수 제약 준수 (clarity) |
| composite | 3 | 2개 | 복합 장애. 런북 2건 필요 |
| unregistered | 3 | 없음 | 미등록 시스템에서 근거 없이 지어내지 않는가 |
| ambiguous | 3 | 없음 | 모호한 요청에서 되묻거나 확인 범위를 밝히는가 |

- 정답 런북이 있는 18건이 검색 지표 대상이다. 나머지 6건은 답변 품질만 본다.
- normal 12건은 설계 구분이 있다 (`design_note`).
  - aligned 6건: 증상과 일치하는 알람을 가진 시스템을 지목한 문항으로 정의했다.
  - paraphrased 6건: 운영자가 자기 말로 증상을 풀어 쓴 문항이다.
  - 질의 문자열을 `monitoring.json` 시스템명과 대조하면 aligned 6건 중 5건이 등록 시스템명을 직접 적고, paraphrased 6건 중 5건은 적지 않는다. 베이스가 질의가 아니라 조사 대상 시스템의 알림으로 런북을 고르기 때문에 이 차이를 둔 것이다.
  - Q01은 aligned로 분류됐으나 시스템명이 없다. 평가셋 고정 원칙에 따라 분류를 고치지 않았다.
- v1은 임시 런북 id와 7건짜리였다. 라벨링과 측정 전에 실제 런북 id 6종과 24건으로 바꿔 v2로 올렸다 (queries.yaml 헤더). v2 이후 질의와 정답은 수정하지 않는다.

### 3.3 측정 축

답변 품질과 검색 품질을 분리해 잰다. 검색이 좋아졌는데 답변이 그대로인 구간을 따로 볼 수 있다.

| 축 | 지표 | 정의 |
|---|---|---|
| 검색 품질 (18건) | Recall@1, Recall@3 | 상위 k개 안의 정답 런북 수 / 정답 수. 복합 장애는 부분 점수 |
| | MRR | 첫 정답의 역순위 |
| | 투입 런북 재현율, 정밀도, 평균 개수 | 순위가 아니라 write에 실제 넣은 런북 기준 |
| | 장애 경로만의 Recall | route가 incident인 건만 집계 |
| 답변 품질 (24건) | 4지표 Pass율, 통과율 | 평가용 Judge. 통과 = 4지표 중 3개 이상 (0.75). 카테고리별 통과율도 낸다 |
| 운영 | 지연 p50, p95 | 그래프 실행 시간. MCP 서버 기동 제외. 선형 보간 백분위 |
| | 토큰, 추정 비용 | 응답의 prompt/completion 토큰을 모델별로 합산 |
| | 재작성 횟수 | `validation_attempts − 1` |
| | 캐시 적중 | lookups 대비 hits |

비용은 실측 토큰에 코드에 적은 공개 단가를 곱한 **추정치**다 (meter.py:24-28).

| 모델 | 입력 USD/1K | 출력 USD/1K |
|---|---|---|
| gpt-4o-mini | 0.00015 | 0.0006 |
| gpt-4o | 0.0025 | 0.01 |
| text-embedding-3-small | 0.00002 | 0 |

- 비용에는 평가용 Judge 호출이 들어가지 않는다. 파이프라인 안의 호출만 센다.
- 런북 색인 임베딩은 1회성이라 질의 계측 시작 전에 만든다 (adapter.py:116-117). 질의별 비용에 포함되지 않는다.
- `retrieved` 는 base에서도 채운다. base는 조회한 런북 1개, RAG는 임베딩 순위 상위 3개다 (adapter.py:104-108). 같은 지표로 비교하기 위한 설계다.

### 3.4 평가용 Judge를 파이프라인 Judge와 분리한다

- 평가용 Judge는 `gpt-4o` 로 고정한다 (`EVAL_JUDGE_MODEL`, run_ablation.py:32). 구성과 무관하다.
- 파이프라인 Validator는 `gpt-4o-mini` 다. 같은 모델이 같은 기준으로 고치고 채점하면 자기채점 순환이 생기므로 모델을 나눴다.
- 입력은 질의, context, 답변 세 가지다. context는 write 노드가 실제로 받은 "수집된 사실" 원문이다 (adapter.py:137-139). 최종 답변을 넣지 않는다. chat 경로로 빠진 건은 고정 문구를 넣는다.
- 평가용 Judge가 JSON을 읽지 못하면 `ParseError` 로 기록하고 해당 건을 통과율 분모에서 뺀다 (eval/judge.py:76-81). 호출 예외는 `judge_error` 에 남기고 다음 건으로 간다 (run_ablation.py:69-74). 지표마다 분모(`n_judged`)를 함께 기록한다.

### 3.5 평가자 검증: 사람 라벨

- 기준 구성 base의 답변 24건에 사람이 Pass/Fail을 매긴다 (`scripts/label.py`).
- 블라인드다. 스크립트는 Judge 판정과 점수를 보여주지 않는다. 질의, 기대 행동, 근거, 답변만 보여준다.
- 판정 기준은 Judge와 같은 4가지다. 묻는 것에 답했나, 근거에 없는 것을 지어냈나, 런북 절차를 반영했나, 요청 형식을 지켰나. 3개 이상 만족하면 Pass다.
- 라벨은 `queries.yaml` 의 `human_label` 에 건별로 저장한다. 라벨을 매긴 답변의 해시는 `eval/labels_meta.json` 에 남긴다. base를 다시 돌려 답변이 바뀌면 리포트가 경고한다 (`eval/report.py` stale_labels).
- 일치율 = (사람 Pass 여부 == Judge 통과 여부) 인 건수 / 라벨과 판정이 모두 있는 건수. base 답변 기준이다 (`eval/report.py` judge_agreement).
- 라벨은 base 답변에만 있다. 다른 구성의 답변에서 일치율이 같다는 보장은 없다.

### 3.6 캐시는 따로 잰다

- Ablation 본 실행은 cold 1회다. 24개 질의는 정규화 후에도 모두 달라서 질의 캐시가 적중할 기회가 없다.
- 그래서 `eval/cache_bench.py` 가 `rag_judge_cost` 구성으로 같은 프로세스에서 24건을 연속 2회 돌린다. 1회차는 cold, 2회차는 캐시가 채워진 상태다.
- 적중 대상은 route, plan, 질의 임베딩뿐이다. 모니터링 조회, write, Judge는 2회차에도 호출된다. 캐시로 줄일 수 있는 범위가 이 세 단계로 한정된다.
- 이 결과는 Ablation 표에 섞지 않고 `results/cache_bench_latest.json` 에서 따로 보고한다.

## 4. 방법론상 주의 (측정 전에 확정한 것)

1. 임계치 0.8 → 0.75. 지표가 4개라 점수는 0, 0.25, 0.5, 0.75, 1 만 가능하다. 0.8 이상은 4개 전부 Pass일 때만 성립한다. "3개 이상 통과"를 의도했으므로 0.75로 고쳤다. 평가셋 v2 작성 시점(측정 전)에 확정했고 모든 구성에 같은 값을 쓴다 (queries.yaml:8).
2. base의 Recall@3 = Recall@1. base는 런북을 1개만 가져와서 `retrieved` 길이가 1이다. RAG는 항상 3개 순위를 남긴다. Recall@3만 비교하면 base에 구조적으로 불리하다. 공정한 비교는 투입 런북 행(재현율, 정밀도)과 Recall@1, MRR로 한다. 런북이 6개뿐이라 top-3은 전체의 절반을 덮는다는 점도 감안한다.
3. Recall은 라우팅을 섞는다. route가 chat으로 빠진 건은 검색 자체가 일어나지 않아 Recall이 0이 된다. 검색 실패와 라우팅 실패를 가르기 위해 장애 경로만의 지표와 그 건수를 함께 낸다 (run_ablation.py:171-178).
4. 모니터링 값이 호출마다 흔들린다. `mcp_server.py:45` 가 CPU에 −3.0~+8.0 난수를 더하고 메모리에는 그 절반을 더한다. 구성끼리 같은 질의라도 답변에 인용되는 CPU, 메모리 수치가 조금 다르다. 상태(`status`)와 알림 문구는 `monitoring.json` 고정값이라 런북 선택에는 영향이 없다.
5. n=24. 통과율 1건은 약 4.2%p 다. 검색 지표는 18건 기준 1건이 약 5.6%p 다. 몇 건 차이로 순위가 뒤집힐 수 있는 크기다.
6. 루브릭이 가깝다. 파이프라인 Judge와 평가용 Judge는 모델은 다르지만 4지표 정의가 거의 같다 (ext/judge.py:25-36, eval/judge.py:24-47). Judge를 쓰는 구성은 평가 기준에 부분적으로 맞춰 최적화되는 구조다. 모델을 나눠도 이 편향은 남는다. 한계로 보고한다.
7. 단일 실행. 구성당 1회만 돌렸다. temperature 0이라도 API 응답과 모니터링 난수는 매번 같지 않다. 반복 실행으로 분산을 재지 않았다.
8. 누적 설계. Judge나 비용 최적화를 RAG 없이 단독으로 켠 구성이 없어서 상호작용은 분리하지 못한다.
9. 사람 라벨은 1명이다. 평가셋과 루브릭을 만든 사람이 라벨도 매겼다. 라벨 자체의 오차는 재지 않았다.
10. 비용 범위. 평가용 Judge 호출과 런북 색인 비용은 비용 추정에서 빠진다 (3.3절).

## 5. 재현 방법

저장소 루트에서 실행한다. Python 3.12 가상환경(`.venv`)을 쓴다. 이 문서를 쓸 때 확인한 것은 `run_ablation`, `report`, `cache_bench` 의 `--help` 출력과 옵션 이름뿐이다. `set_keys.sh`, `pytest`, `label.py` 와 API를 호출하는 실행은 이 문서를 쓰는 과정에서 돌리지 않았다.

```bash
# 1. 키 입력 (화면에 표시하지 않고 .env 에 저장. .env 는 커밋하지 않는다)
scripts/set_keys.sh

# 2. 오프라인 배관 테스트 (fake 백엔드, API 호출 없음)
.venv/bin/python -m pytest -q tests/

# 3. 4구성 실측 (base → rag → rag_judge → rag_judge_cost 순서, 구성별 24건)
.venv/bin/python -m eval.run_ablation --all
#    구성 하나만: --config eval/configs/rag.yaml
#    일부 질의만: --ids Q01,Q05 (결과 파일은 저장하지 않는다)

# 4. 사람 라벨 (3번이 끝나 results/base_latest.json 이 있어야 한다)
.venv/bin/python scripts/label.py

# 5. 캐시 효과 (rag_judge_cost 구성, 24건 × 2회)
.venv/bin/python -m eval.cache_bench

# 6. 비교표와 Judge 일치율
.venv/bin/python -m eval.report --md
```

- 결과 파일: `results/{구성}_{YYYYMMDD_HHMM}.json` 과 `results/{구성}_latest.json`. 실행 중에는 건마다 `results/{구성}_partial.json` 에 중간 저장한다.
- `--backend fake` 와 `--no-judge` 결과는 `_latest` 를 덮어쓰지 않는다 (run_ablation.py:203-205).
- 라벨은 마지막 base 실행 이후에 매긴다. base를 다시 돌리면 답변이 바뀌어 라벨과 어긋날 수 있다.
- LangSmith 추적은 `.env` 의 `LANGCHAIN_TRACING_V2=true` 일 때만 `trace_url` 에 기록된다.
