## A안 — 8장 덱 (5분)

### 1장 표지 (0:00 → 0:10)

> 광주 2반 장병헌입니다. 장애 대응 에이전트 개선 과제를 발표하겠습니다.

### 2장 한 장 요약 (0:10 → 0:35)

> 한 장으로 먼저 보여드리겠습니다. 새벽 당직자가 "DB가 다운됐다"고 물어도 원본 AI 비서는 응답 지연 매뉴얼을 꺼냈습니다. 저는 고친 부분을 **하나씩 켜고 끄며 무엇이 실제로 효과였는지**를 쟀고, 채점하는 AI도 검사했습니다. 결과는 오른쪽 숫자 다섯 개입니다.

### 3장 실태 현황 (0:35 → 1:05)

> 왜 이 방식인지부터 말씀드리겠습니다. 장애는 비쌉니다. 응답자 54%가 중대 장애 비용이 10만 달러를 넘었다고 답했습니다. 시장은 이미 AI SRE로 가고 있고 PagerDuty, Datadog, AWS 같은 제품이 정식 출시됐는데, 구조는 런북 근거, MCP, 사람 승인으로 제 과제와 같습니다. 그런데 공개된 효과 수치는 대부분 "최대 몇 %"인 업체 주장이고, 국내 공개 사례 중 Ablation을 공개한 곳은 찾지 못했습니다. 저는 그 빈칸을 채웠습니다.

### 4장 문제 1 (1:05 → 1:40)

> 원본은 질문을 읽지 않고 모니터링 알림 문구의 키워드로 매뉴얼을 고릅니다. 알림에 latency가 있으니 응답 지연 매뉴얼을 고르고 커넥션 풀을 늘리라고 답합니다. 그래서 맞는 매뉴얼 누락이 56%였고, 알림 문구대로 물으면 78%를 맞히지만 자기 말로 물으면 11%였습니다.

### 5장 결론 (1:40 → 2:15)

> 결론은 세 가지입니다. RAG로 질문 의미로 찾게 하자 누락이 56%에서 9%로 줄었습니다. 캐스케이드로 장애 1건 비용이 캐스케이드만으로 73%, 최종 구성에서 84% 줄었습니다. 많이들 넣는 LLM Judge 검수는 품질 향상이 확인되지 않았고 지연만 2.3초 늘었습니다.

### 6장 개선별 기여도 (2:15 → 3:20) — 핵심

> 60문제 중 36문제는 기준을 정하기 전에 커밋으로 고정한 holdout이고, 7가지 구성을 3번씩 돌려 1,260회 실행했습니다. 같은 문제끼리 짝지어 "켰을 때 빼기 껐을 때"를 신뢰구간으로 봤고, 별표가 0을 포함하지 않는 효과입니다.
> 품질 별표는 RAG 행에 몰려 있습니다. 누락 -46%p입니다. 1차 실험에서 RAG가 엉뚱한 매뉴얼도 섞는 걸 발견해 v2 기준으로 혼입을 -24%p 줄였습니다. Judge 행에는 비용과 지연 별표만 있습니다. 문헌도 같습니다. 외부 피드백 없는 자기 검수는 효과가 없다는 연구가 있습니다.
> 평가 Judge도 후해서, 결론은 코드로 센 지표로 냈습니다. 독립 평가자로 대조해 보니 불합격 답의 59%를 합격시켰습니다.

### 7장 시연 (3:20 → 4:00)

> 같은 질문의 실제 실행 기록입니다. 원본은 응답 지연 매뉴얼로 커넥션 풀을 늘리라고 하고, 최종은 DB 다운 매뉴얼로 failover 전환을 권합니다. 실제 API로 잰 운영 지표도 있습니다. 동시 질문 10개가 62.8초에서 9.2초로 줄었고, 조회 30%를 일부러 실패시켰을 때 원본은 0건, 최종은 18건 모두 끝까지 처리했습니다.

### 8장 한계 (4:00 → 4:50)

> 한계도 분명합니다. 자기 말로 묻는 질문의 1순위 정답률은 33%이고, 엉뚱한 매뉴얼 혼입이 35% 남았습니다. 다음은 증상 예시 문장 색인과 재순위입니다. 현업에 붙인다면 조사와 매뉴얼 검색은 읽기 전용 MCP로 바꾸고, 쓰는 단계에만 사람 승인을 붙이겠습니다.

### 마무리 (4:50 → 5:00)

> 기능을 더하기 전에 효과를 재는 법부터 만들었습니다. 코드와 결과, 조사 근거는 README에 모두 있습니다. 감사합니다.

| Vector DB는 왜 안 썼나요? | 런북이 6개라 임베딩을 디스크에 캐시하고 메모리에서 코사인 순위를 매겼습니다. 문서가 늘면 같은 인터페이스(`RunbookRetriever`)로 Vector DB를 붙이면 됩니다. (`src/ext/rag.py`) |

| holdout을 나중에 고친 건 아닌가요? | holdout은 커밋 `6eb9482`(11:16)로 고정했고 v2 코드는 `c0ec157`(11:36)로 그 뒤입니다. 커밋 시각으로 확인됩니다. |
| 최종이 원본보다 느린데요? | 질의당 +1.4초입니다. RAG 검색과 검수 비용입니다. 다만 +비용·final은 캐시 버그 수정 뒤 더 가벼운 부하에서 다시 쟀기 때문에 지연 차이에는 부하 차이가 섞였을 수 있다고 README에 적었습니다. |
| 사람이 직접 검증했나요? | 아니요. 독립 평가자는 Claude(AI)이고, 사람 표본 채점 도구(`scripts/label.py`)는 준비했지만 아직 하지 않았습니다. 그래서 결론은 AI 채점이 아니라 코드로 센 지표로 냈습니다. |
| 비용 -84%는 캐스케이드 덕인가요? | 캐스케이드만 켜면 -73%입니다. 최종 -84%는 v2·런타임 개선까지 더해 재작성이 사라진 구성의 값이라, 나머지 차이를 어느 개선이 만들었는지는 분리하지 않았습니다. |
| 도구 고장 때 답의 품질은요? | 끝까지 처리했는지만 쟀고 그 답의 품질은 평가하지 않았습니다. 실패한 조회는 근거에 실패로 표시하고 나머지 근거로 답합니다. |
| 이미 AWS·Datadog·PagerDuty가 다 하는데, 이 과제의 의미는? | 구조는 현업과 같습니다(런북 RAG·MCP·사람 승인, README 1.2). 다른 점은 효과를 재는 방법입니다. 공개 수치 대부분이 "최대 몇 %" 업체 주장이나 PoC이고, 국내 공개 사례에서 고정 평가셋·Ablation은 찾지 못했습니다. Datadog도 기능 하나가 다른 조사를 나쁘게 만든 사례를 공개했는데, 저는 그걸 부품별로 분리해 쟀습니다. (docs/research/) |

## 교수·현업 SRE 관점 예상 질문 10 (ChatGPT로 만들고 수치를 원자료로 정정)

| # | 질문 | 30초 답 |
|---|---|---|
| 1 | 1,260회를 독립 표본으로 볼 수 있나? | 아닙니다. 1,260회는 7구성 x 60문제 x 3회의 실행 횟수입니다. 구성 간 비교는 같은 문제를 단위로 3회 평균을 내고 짝지은 bootstrap으로 했습니다. 문제 수(holdout 36)가 실제 표본입니다. |
| 2 | 표는 56%→9%(47%p)인데 기여도는 -46%p, 왜 다른가? | 분모가 다릅니다. 표는 반복마다 장애로 처리된 질문 전체의 비율(원값 56.28%→8.57%)이고, 기여도는 두 구성 모두 장애로 처리된 같은 질문 23개만 짝지어 계산했습니다(-46.38%p). 혼입도 같아서 표 65%→35%, 짝지은 값 -28.7%p(29문제)입니다. |
| 3 | 결과를 보고 고쳤으면 누수 아닌가? | 그래서 나눴습니다. v2 기준값은 dev 24문제로만 정했고, holdout 36문제는 v2 구현 전에 커밋(6eb9482, 11:16)으로 고정했습니다. v2 코드는 그 뒤(c0ec157, 11:36)입니다. |
| 4 | 런북 6개, Vector DB도 없는데 RAG인가? | RAG의 핵심은 검색 결과를 생성에 넣는 것이고, 저장소 종류는 아닙니다. 6개라 메모리 인덱스로 충분했습니다. 문서가 많을 때의 검색 성능은 재지 않았습니다. |
| 5 | 최소 유사도 기준이 정답까지 버린 것 아닌가? | 확인했습니다. v2를 켜도 맞는 매뉴얼 누락은 그대로(변화 0%p)였고 혼입만 -24%p(59%→35%) 줄었습니다. 다만 기준값은 경계값입니다. dev에서 맞는 매뉴얼이 있는 질문과 없는 질문의 점수 차이가 0.0023뿐이라, 운영 최적값이라고 주장하지 않습니다. |
| 6 | 효과 없는 Judge를 왜 넣었나? | 넣으면 좋아지는지 확인하려고 독립 구성으로 쟀고, 품질 향상은 확인되지 않고 지연만 +2.3초였습니다. 그래서 LLM 자기 검수 대신 코드로 하는 사실 확인(factcheck)을 다음 방향으로 정했습니다. 외부 피드백 없는 자기교정은 효과가 없다는 연구(Huang 외, ICLR'24)와 같은 결과입니다. |
| 7 | kappa 0.39면 평가를 믿을 수 있나? | 그래서 평가 Judge 점수로 결론을 내지 않았습니다. 결론은 코드로 센 지표(누락·혼입·핵심 문구)로 냈고, kappa는 평가 Judge가 후하다는 증거로 썼습니다. 독립 평가자도 AI(Claude)이고 사람 채점은 하지 않았습니다. |
| 8 | 비용·속도는 같은 조건 비교인가? | 비용(-73%·-84%)은 같은 질문·같은 단가로 계산한 추정치입니다. 동시 질문 62.8초→9.2초는 같은 final 구성에서 동기/비동기만 바꾼 같은 벤치라 조건이 같습니다. 다만 Ablation 표의 지연은 +비용·final을 더 가벼운 부하에서 다시 재서 부하 차이가 섞였을 수 있습니다. |
| 9 | 도구 30% 고장에도 완주했으면 운영에 붙여도 되나? | 아닙니다. 완주 여부만 1회 쟀고 답 품질은 평가하지 않았습니다. 고장 맞은 질문 수(19, 18)도 실행마다 달랐습니다. 운영에는 읽기·쓰기 권한 분리, 쓰기 전 사람 승인, 감사 로그, 프롬프트 인젝션 차단이 먼저 필요합니다. |
| 10 | 본인 기여와 재현성은? | 원본 노드는 그대로 두고 스위치로 교체하는 확장(src/ext), 평가 하네스(eval/), 측정 7구성과 벤치가 기여입니다. scripts/run_all.sh 하나로 다시 돌릴 수 있고 오프라인 테스트 25개가 통과합니다. 실행 오류 0이 답의 정확성을 보장하지는 않습니다. |
