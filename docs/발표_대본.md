## A안 — 6장 덱 (5분)

### 1장 표지 (0:00 → 0:25)

> 광주 2반 장병헌입니다. 저는 교수님 베이스 장애 대응 에이전트를 개선했는데, 개선을 많이 붙이는 것보다 **어떤 개선이 실제로 효과였는지를 통계로 가려내는 것**에 집중했습니다. 그리고 채점한 AI가 얼마나 후한지도 따로 쟀습니다.

### 2장 문제 1 (0:25 → 1:15)

> 먼저 문제입니다. 당직자가 "DB 프라이머리가 다운됐다"고 물어도, 원본은 질문을 읽지 않고 모니터링 알림 문구의 키워드로 매뉴얼을 고릅니다. 알림에 latency가 있으니 응답 지연 매뉴얼을 고르고, 커넥션 풀을 늘리라고 답합니다.
> 그래서 holdout에서 맞는 매뉴얼을 못 넣은 비율이 56%였고, 알림 문구대로 물으면 78%를 맞히지만 자기 말로 물으면 11%였습니다. 또 원본 검수는 "30자 이상, 1) 포함"만 봐서 이런 답도 통과시켰습니다.

### 3장 결론 (1:15 → 2:05)

> 결론부터 말씀드리면 세 가지입니다.
> 하나, RAG로 질문 의미로 매뉴얼을 찾게 하자 누락이 56%에서 9%로 줄었습니다.
> 둘, 싼 모델로 먼저 쓰고 반려될 때만 비싼 모델을 쓰는 캐스케이드로, 장애 1건 비용이 캐스케이드만으로 73%, 최종 구성에서 84% 줄었습니다.
> 셋, 많이들 넣는 LLM Judge 검수는 품질 향상이 확인되지 않았고 지연만 2.3초 늘었습니다.
> 실제 API로 잰 운영 지표도 있습니다. 동시 질문 10개가 62.8초에서 9.2초로 줄었고, 모니터링 조회 30%를 일부러 실패시켰을 때 원본은 0건, 최종은 18건 모두 끝까지 처리했습니다.
> 이 숫자를 어떻게 믿을 수 있는지가 다음 장입니다.

### 4장 개선별 기여도 (2:05 → 3:20) — 핵심

> 평가셋 60문제 중 36문제는 개선 기준을 정하기 전에 커밋으로 고정한 holdout이고, 7가지 구성을 3번씩 돌려 1,260회 실행했습니다. 같은 문제끼리 짝지어 "켰을 때 빼기 껐을 때"를 bootstrap 신뢰구간으로 봤고, 별표는 신뢰구간이 0을 포함하지 않는다는 뜻입니다.
> 보시면 품질 별표는 RAG 행에 몰려 있습니다. 누락 -46%p입니다. 1차 실험에서 RAG가 엉뚱한 매뉴얼도 섞는 걸 발견해서, 최소 유사도 기준을 넣은 v2로 혼입을 -24%p 줄였습니다.
> 반면 Judge 행에는 비용과 지연 별표만 있습니다. 개선을 한꺼번에 붙였다면 RAG 효과를 Judge 효과로 착각했을 겁니다.
> 그리고 평가 Judge가 대부분 구성에 90% 넘게 합격을 줘서, 결론은 코드로 센 지표로 냈습니다. 독립 평가자로 대조해 보니 평가 Judge는 불합격 답의 59%를 합격시켰습니다.

### 5장 시연 (3:20 → 4:05)

> 같은 질문을 원본과 최종에 넣은 실제 실행 기록입니다. 원본은 응답 지연 매뉴얼을 골라 커넥션 풀을 늘리라고 하고, 최종은 DB 다운 매뉴얼을 골라 failover 전환을 권합니다. 디스크 부족 매뉴얼도 같이 들어간 건 아직 남은 혼입 문제입니다. 비용은 0.0028달러에서 0.00046달러였습니다.

### 6장 한계 (4:05 → 4:50)

> 한계도 분명합니다. 자기 말로 묻는 holdout 질문의 Recall@1은 33%로, dev와 holdout 사이에 일반화 격차가 있습니다. 엉뚱한 매뉴얼 혼입이 35% 남았고, 캐스케이드는 매뉴얼 문구 인용이 5%p 줄었습니다(유의하지 않음). 다음은 증상 예시 문장 색인과 재순위로 이 두 가지를 줄이는 것입니다.

### 마무리 (4:50 → 5:00)

> 기능을 더하기 전에 효과를 재는 법부터 만들었습니다. 코드와 결과는 README에 모두 있습니다. 감사합니다.

## 예상 질문과 답

| 질문 | 답 (근거) |
|---|---|
| Vector DB는 왜 안 썼나요? | 런북이 6개라 임베딩을 디스크에 캐시하고 메모리에서 코사인 순위를 매겼습니다. 문서가 늘면 같은 인터페이스(`RunbookRetriever`)로 Vector DB를 붙이면 됩니다. (`src/ext/rag.py`) |
| Judge가 효과가 없다는 건가요? | "품질 향상이 확인되지 않았다"입니다. 신뢰구간이 0을 포함했고, 지연·비용만 유의하게 늘었습니다. v2 보완의 혼입 -24%p는 검색 단계 지표라 Judge가 아니라 최소 유사도 기준에서 나온 것입니다. |
| holdout을 나중에 고친 건 아닌가요? | holdout은 커밋 `6eb9482`(11:16)로 고정했고 v2 코드는 `c0ec157`(11:36)로 그 뒤입니다. 커밋 시각으로 확인됩니다. |
| 최종이 원본보다 느린데요? | 질의당 +1.4초입니다. RAG 검색과 검수 비용입니다. 다만 +비용·final은 캐시 버그 수정 뒤 더 가벼운 부하에서 다시 쟀기 때문에 지연 차이에는 부하 차이가 섞였을 수 있다고 README에 적었습니다. |
| 사람이 직접 검증했나요? | 아니요. 독립 평가자는 Claude(AI)이고, 사람 표본 채점 도구(`scripts/label.py`)는 준비했지만 아직 하지 않았습니다. 그래서 결론은 AI 채점이 아니라 코드로 센 지표로 냈습니다. |
| 비용 -84%는 캐스케이드 덕인가요? | 캐스케이드만 켜면 -73%입니다. 최종 -84%는 v2·런타임 개선까지 더해 재작성이 사라진 구성의 값이라, 나머지 차이를 어느 개선이 만들었는지는 분리하지 않았습니다. |
| 도구 고장 때 답의 품질은요? | 끝까지 처리했는지만 쟀고 그 답의 품질은 평가하지 않았습니다. 실패한 조회는 근거에 실패로 표시하고 나머지 근거로 답합니다. |
