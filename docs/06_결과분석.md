# 결과 분석

모든 수치의 출처는 `results/{구성}_latest.json` (2026-10-21 10:33~10:45 실행, 4구성 x 24건 = 96회, 실행 오류 0)이다.
표 전체는 `python -m eval.report --md` 로 다시 만들 수 있다 (`docs/04_결과표.md`).
평가셋 24건이라 질의 1건 = 4.2%p, gold 런북이 있는 18건 기준 1건 = 5.6%p다. 아래 해석은 이 해상도를 넘지 않게 쓴다.

## 1. 한 장 요약

| 지표 | base | rag | rag_judge | rag_judge_cost | 출처 |
|---|---|---|---|---|---|
| Recall@1 (gold 18건) | 36% | 72% | 72% | 72% | summary.recall@1 |
| 투입 런북 정밀도 | 53% | 78% | 78% | 78% | summary.fed_precision |
| 런북 핵심 어구 포함률 (Judge 무관) | 36% | 80% | 88% | 84% | eval/answer_metrics.py |
| 평가 Judge 통과율 (gpt-4o) | 83% | 100% | 96% | 96% | summary.pass_rate |
| 재작성 합계 | 0 | 0 | 6 | 3 | summary.rewrites_total |
| 지연 p95 (ms) | 6,833 | 7,339 | 18,121 | 11,739 | summary.latency_p95_ms |
| 추정 비용 (USD, 24건) | 0.0647 | 0.0731 | 0.1118 | 0.0264 | summary.cost_usd_total |

비용은 OpenAI 공개 단가 x 실측 prompt/completion 토큰으로 낸 추정치이며, 평가용 Judge(gpt-4o) 호출과 런북 색인 1회 임베딩 비용은 뺐다.

**결론 세 줄**

1. 품질 개선은 거의 전부 RAG에서 나왔다. 검색 Recall@1이 36%에서 72%로, 답변의 런북 어구 포함률이 36%에서 80%로 올랐다.
2. 파이프라인 Judge(gpt-4o-mini)는 이 평가셋에서 측정 가능한 품질 향상을 만들지 못했고, 비용을 53% 늘리고 p95 지연을 2.5배로 키웠다.
3. 1차 초안을 gpt-4o-mini로 쓰고 반려될 때만 gpt-4o로 다시 쓰는 캐스케이드는 rag_judge 대비 비용을 76% 줄였고(base 대비 59% 절감), 품질 지표는 노이즈 범위 안에서 같았다.

## 2. RAG — 개선의 대부분

### 원인: base 의 런북 선택은 질의를 보지 않는다

base 는 조사한 시스템의 모니터링 알림 문구에서 키워드를 찾아 런북 1개를 고른다 (`src/agent/graph.py:192-213`).
질의에 시스템 이름이 없으면 planner 가 auth-service 로 폴백하고, auth-service 알림에는 `p95 latency` 가 있다.
그 결과 base 가 장애 경로로 처리한 20건 중 **15건이 high-latency 런북**을 받았다 (`results/base_latest.json` rows.retrieved).
"DB 프라이머리가 다운됐습니다"(Q01), "서버 저장공간이 거의 꽉 찼다"(Q06)도 응답 지연 절차로 답했다.

### 효과

| 지표 | base | rag | 변화 |
|---|---|---|---|
| Recall@1 | 36% | 72% | +36%p |
| Recall@1 (장애 경로 15건만) | 43% | 87% | +43%p |
| MRR | 0.444 | 0.806 | +0.361 |
| 투입 런북 재현율 | 36% | 78% | +42%p |
| 투입 런북 정밀도 | 53% | 78% | +24%p |
| 런북 핵심 어구 포함률 | 36% | 80% | +44%p |
| normal 카테고리 평가 Judge 통과율 | 75% | 100% | +25%p |

Recall@3 는 base 가 런북을 1개만 고르므로 구조적으로 Recall@1 과 같다. 공정한 비교는 write 에 실제로 넣은 런북 기준인 '투입 런북' 행이다.
RAG 순위는 세 RAG 구성에서 완전히 같았다 (임베딩이 결정적). 구성 간 차이는 검색 이후 단계에서만 생긴다.

### 비용

RAG 는 질의 임베딩 1회와 더 긴 근거를 추가해 비용을 13% 늘렸다 ($0.0647 → $0.0731). p50 지연 차이는 79ms다.

### RAG 의 한계 (실측)

- **최소 유사도 기준이 없다.** 미등록 질의(Kafka 컨슈머 랙, PG사 API, SSL 인증서)에도 런북을 1~3개 넣는다. 평균 투입 수가 0.83개에서 1.33개로 늘어난 것도 이 때문이다.
- **라우팅 실패는 고치지 못한다.** 형식 제약 질의 3건(Q13~15)과 모호 질의 1건(Q23)은 원본 라우터가 4구성 모두에서 chat 으로 보냈다. 검색 자체가 일어나지 않았고, 답에는 런북 절차가 없다 (Q14 어구 포함 0/1, 4구성 동일).

## 3. 파이프라인 Judge — 측정 가능한 이득 없음, 비용은 큼

### 무엇을 반려했나

rag_judge 의 재작성 6회는 Q20·Q21·Q22 세 건에서만 일어났다. 셋 다 미등록·모호 질의다.
Judge 는 "Kafka 컨슈머 랙 대응 절차가 반영되지 않았다"처럼, **근거(런북)에 없는 절차를 요구하며** 반려했다 (`results/rag_judge_latest.json` rows.pipeline_judge).
런북에 없는 내용이라 재작성으로 충족할 수 없고, Q21 은 재시도 상한(2회)에서 가드가 멈췄다.
Q20 은 재작성 후 답이 "Kafka 문제를 해결하기 위해 auth-service 를 점검한다"는 식으로 질문과 근거를 억지로 이어 붙였고, 평가 Judge 는 이 답을 Fail 로 봤다 (rag 에서는 같은 질의가 Pass).

정상 질의 12건에서는 한 번도 반려하지 않았다. 원본 규칙 Validator 도 4구성 전체에서 한 번도 반려하지 않았다 (gpt-4o 답은 항상 30자 이상이고 "1)"을 포함).

### rag → rag_judge 의 어구 포함률 +8%p 는 Judge 효과가 아니다

차이는 Q08·Q10 두 건(어구 2개)에서 났는데, 두 건 모두 rag_judge 에서 재작성이 0회였다.
즉 Validator 가 개입하기 전의 1차 초안끼리 차이이고, 같은 설정을 두 번 돌릴 때 생기는 변동이다.
모니터링 값은 호출마다 무작위로 흔들리고 (`src/mcp_server.py:45`), LLM 출력도 temperature 0 에서 완전히 같지 않다.
**이 평가셋에서 실행 간 변동은 어구 26개 중 2개(약 8%p) 수준**으로 보고, 그보다 작은 차이는 결론에 쓰지 않는다.

### 비용과 지연

| | rag | rag_judge | 변화 |
|---|---|---|---|
| 추정 비용 | $0.0731 | $0.1118 | +53% |
| 지연 p95 | 7,339ms | 18,121ms | 2.5배 |
| gpt-4o write 호출 | 20 | 26 | +6 (재작성) |
| Judge 호출 (gpt-4o-mini) | - | 26 | 약 $0.006 |

비용 증가의 대부분은 Judge 호출 자체가 아니라 Judge 가 유발한 gpt-4o 재작성에서 나온다.

### 해석

Judge 를 붙이는 것만으로는 품질이 오르지 않았다. 이 평가셋에서 정상 질의의 1차 답은 이미 기준을 넘었고, Judge 가 반려한 것은 런북이 없는 질의였다.
Judge 기준에 "근거에 해당 절차가 없으면 없다고 밝히는 것이 정답"이라는 조건이 빠져 있어, 정직한 답을 오히려 반려하는 방향으로 작동했다.
다음 개선은 Judge 반려 사유를 "근거 안에서 고칠 수 있는 것"과 "근거 밖의 요구"로 나누고, 후자는 재작성 대신 '미등록' 안내로 보내는 것이다.

## 4. 캐스케이드 — 비용 76% 절감, 품질 유지

| | rag_judge | rag_judge_cost | 변화 |
|---|---|---|---|
| 추정 비용 | $0.1118 | $0.0264 | -76% |
| 지연 p95 | 18,121ms | 11,739ms | -35% |
| write 호출 | gpt-4o 26 | gpt-4o-mini 20 + gpt-4o 3 | |
| 재작성 | 6 | 3 | |
| 평가 Judge 통과율 | 96% | 96% | 0 |
| 런북 핵심 어구 포함률 | 88% | 84% | -4%p (어구 1개, 노이즈 범위) |

1차 초안을 gpt-4o-mini 로 써도 20건 중 17건이 파이프라인 Judge 를 바로 통과했다. gpt-4o 는 반려된 3건의 재작성에만 쓰였다.
base 와 비교하면 비용은 59% 줄고 ($0.0647 → $0.0264) 런북 어구 포함률은 36% → 84%다.
처음 계획한 '역할별 모델 분리'는 base 에 이미 들어 있었다 (fast=gpt-4o-mini, quality=gpt-4o, `src/server.py:50-56`). 그래서 비용 축을 캐스케이드로 다시 정의했다.

## 5. 캐시

출처: `results/cache_bench_latest.json` (`python -m eval.cache_bench`, rag_judge_cost 구성, 같은 24건을 같은 프로세스에서 2회 연속 실행).

| | 1회차 | 2회차 | 변화 |
|---|---|---|---|
| 캐시 적중 (route·plan·질의 임베딩) | 0/64 | 64/64 | |
| 입력 토큰 | 42,912 | 30,665 | -29% |
| 추정 비용 | $0.0204 | $0.0141 | -31% |

Ablation 본 실행(cold 1회)에서는 정규화 후 24개 질의가 모두 달라 캐시가 한 번도 맞지 않는다. 그래서 캐시 효과는 Ablation 표에 섞지 않고 따로 쟀다.
같은 알림을 여러 사람이 반복해 묻는 상황에서만 효과가 있다. 정규화는 대소문자·공백·문장부호만 흡수하므로 문장이 조금만 달라도 적중하지 않는다.
모니터링 값과 최종 답변은 캐시하지 않는다 (장애 상태는 호출마다 바뀐다). write·Judge 호출이 그대로 남아 있어 절감 폭은 비용의 일부에 그친다.
대가: TTL 600초 동안은 런북이 바뀌어도 옛 route·plan·임베딩을 쓴다.

## 6. 평가자 검증

### 평가 Judge 는 관대했다

- 근거가 비어 있는 chat 답(Q13, Q14)에 completeness Pass 를 줬다. 근거가 없으니 "지어낸 게 없다"는 판정이다. 답에는 런북 절차가 없다.
- rag 의 Q20 답은 Kafka 질문에 auth-service 응답 지연 절차만 말했는데 4지표 모두 Pass 였다.
- base 에서 런북을 틀리게 붙인 Q08·Q10·Q12 도 Pass 였다.

평가 Judge 통과율은 rag 에서 100%로 포화돼 구성 간 차이를 거의 보여주지 못한다. 그래서 Judge 와 무관한 결정적 지표(런북 핵심 어구 포함률)를 함께 본다.
이 어구는 평가셋 v2 를 만들 때 (측정 전) 정답 런북 본문에서 뽑아 둔 것이며, 측정 후 저장된 답변을 다시 채점했을 뿐 재실행하지 않았다.
표현만 바꾼 경우(예: failover → 페일오버)는 놓치므로 하한 지표다.

## 7. 한계

- **n=24, 1회 실행.** 1건 = 4.2%p. 실행 간 변동이 어구 기준 약 8%p 관찰됐다. 반복 실행으로 분산을 재지 못했다.
- **평가 Judge 포화.** 품질 차이는 결정적 지표와 사람 라벨로 보완했다.
- **파이프라인 Judge 와 평가 Judge 의 기준이 비슷하다.** 모델만 다르다 (gpt-4o-mini vs gpt-4o). Judge 구성은 평가 기준에 맞춰 최적화되는 방향이 있다. 그런데도 이득이 없었다는 것은 오히려 결론을 강하게 한다.
- **라우터는 개선 대상에서 빠졌다.** 형식 제약 질의가 chat 으로 빠지는 문제는 4구성 모두 같다.
- **비용은 추정.** 공개 단가 기준이며 실제 청구액이 아니다.
