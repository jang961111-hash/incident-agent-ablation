# 결과 분석

7구성 x 60건 x 3회 = 1,260회 실행, 실행 오류 0 (`results/{구성}_latest.json`, `results/raw/run_all_v2.log`). 이 중 rag_judge_cost와 final의 2회차 120회는 캐시 오염으로 집계에서 뺐다. 이 두 구성은 반복 2회(1·3회차)로, 나머지 5구성은 3회로 집계한다(집계 1,140회).
평가셋은 dev 24건(Q01~Q24, 개선 v2의 기준값 조정에 사용)과 holdout 36건(Q25~Q60, 조정에 쓰지 않음)이다.
holdout 문항은 개선 v2 구현 전에 커밋했다 (`eval/queries.yaml` 6eb9482, 2026-10-21 11:16; v2 코드 c0ec157, 11:36). 최종 판단은 holdout 수치로 한다. dev 수치는 비교용으로만 쓴다.
평가 Judge는 gpt-4o이고, 파이프라인 안의 Judge는 gpt-4o-mini다 (`eval/configs/*.yaml`).

**캐시 오염과 집계 제외.** v2 실측에서 rag_judge_cost와 final의 2회차에만 앞 반복의 캐시가 적중했다 (2회차 60건 전체에서 각각 160회, 158회. 1·3회차는 0회). 반복 사이에 캐시가 비워지지 않은 버그이고 99c80d1에서 고쳤다. 오염된 2회차는 `eval/exclude_reps.py`(f230443)로 집계에서 뺐다. 행은 지우지 않고 `excluded_rows`에 두었고 사유는 `summary.excluded_reps`, `summary.exclusion_reason`에 적혀 있다.

반복을 cold로 다시 재려 했으나 실측에 쓴 OpenAI 프로젝트(개인 프로젝트, 월 한도 $10)가 지출 한도에 걸려(`project_spend_limit_exceeded`) 재측정하지 못했다. 그래서 두 구성은 반복 2회다. 반복 간 ±는 t(df=1)=12.7을 곱해 매우 넓다. 이 문서의 두 구성 수치와 이 둘이 낀 모든 bootstrap 비교는 제외 후 값이다. 이전 판에서 "캐스케이드+캐시로 지연이 −0.8초 줄었다", "v2 위 비용·런타임으로 −1.1초 줄었다"고 쓴 것은 캐시가 적중한 반복이 섞인 값이었다. 제외 후 각각 −0.1초(유의하지 않음), −0.4초(유의)다. 캐시 효과는 6절 캐시 벤치에서 따로 본다.

읽는 규칙은 다음과 같다.

- 표의 `±`는 반복 간 95% 신뢰구간 반폭이다 (`python -m eval.report`). 퍼센트는 %p다. rag_judge_cost와 final은 반복이 2회라 ±가 크다.
- 구성 간 차이는 질의 단위 paired bootstrap(2,000회, 질의별 값은 반복 평균. 두 구성은 2회 평균)의 95% CI로 판정한다 (`results/stats_holdout.json`).
- "유의하다"는 이 CI가 0을 포함하지 않는다는 뜻이다. 0을 포함하면 "차이가 있다고 말할 수 없다"고 쓴다. 차이가 없다는 뜻은 아니다.
- 비교 49개(7쌍 x 7지표)에 다중 비교 보정을 하지 않았다. 하한이 0에 가까운 유의 결과는 약하게 읽는다.

- 비용은 OpenAI 공개 단가 x 실측 토큰의 추정치다. 평가 Judge 호출과 런북 색인 임베딩은 뺐다.
- 지연은 7구성을 동시에 돌린 부하에서 쟀다. 절대값이 아니라 구성 간 상대 비교로만 쓴다.

**결론**

1. 품질은 검색(RAG)에서 나왔다. base → rag에서 정답 런북 누락 56% → 9%, 런북 어구 포함 45% → 81%, Recall@1 33% → 52%가 모두 유의하다. Judge를 얹은 구성들은 이 지표들에서 RAG만 쓴 구성과 차이가 있다고 말할 수 없다.
2. 파이프라인 Judge는 품질을 올리지 못하고 비용과 지연만 유의하게 늘렸다. RAG 위에 Judge를 얹으면 질의당 +$0.0005, 질의당 지연 +1.8초다.
3. 캐스케이드(1차 초안 gpt-4o-mini)는 건당 비용을 $0.00464에서 $0.00086으로 낮췄다(−81%). 어구 포함은 78% → 72%로 점추정이 낮지만 CI가 넓어(−19~+8%p) 차이가 있다고 말할 수 없다. 지연은 줄지 않았다(−0.1초, 차이가 있다고 말할 수 없음). 비용 절감은 캐스케이드에서 나왔고, 캐시는 이 측정에서 적중이 없었다.
4. v2 보완은 무관 런북 혼입을 59% → 35%로 낮췄다(−24%p, 유의). 누락, 어구 포함, Judge 통과율은 차이가 있다고 말할 수 없다.
5. base → final은 누락 −46%p, 혼입 −30%p, 어구 포함 +31%p, 질의당 비용 −$0.0023이 유의하다(장애 1건당 비용으로는 $0.00343 → $0.00064, −81%). 질의당 지연은 +1.8초 유의하게 늘었다. 남은 약점은 혼입 34%, Recall@1 54%(질의를 자기 말로 푼 경우 33%), 누락 9%다.
6. 지연은 base보다 느리다. v2 → final에서 −0.4초가 유의하게 줄었지만(캐스케이드·비동기 I/O·도구 부분 실패 허용을 한꺼번에 켠 구성이라 하나로 귀속하지 못한다), base → final은 +1.8초다. 캐시는 같은 질의를 반복해 물을 때만 효과가 있고(6절 캐시 벤치: 적중 70%, p50 7.9초 → 5.6초) 7구성 비교에서는 효과를 재지 못했다.

해석은 행별로 다음과 같다.

- **RAG 단독.** 정답 런북을 근거에 넣는 비율이 오르면서 누락, 어구 포함, Recall@1, 평가 Judge 통과가 모두 유의하게 좋아졌다. 혼입은 차이가 있다고 말할 수 없다. 투입 런북 수가 평균 0.85개에서 1.46개로 늘어(`summary.by_split.holdout.mean.fed_count_mean`) 맞는 런북을 넣는 만큼 무관한 런북도 함께 들어갔기 때문이다. 비용과 지연은 유의하게 늘었지만 폭은 작다 (+$0.0004, +0.4초).
- **Judge 단독.** 품질 5지표 모두 차이가 있다고 말할 수 없다. Judge는 이미 고른 런북을 바꾸지 못하므로 누락이 그대로인 것은 구조상 당연하다. 비용(+$0.0009)과 지연(+2.3초)은 유의하게 늘었다. 재작성이 반복당 7.0회 일어났다.
- **RAG 위에 Judge.** 검색 지표는 두 구성이 같다. 어구 포함과 통과율 모두 차이가 있다고 말할 수 없고, 비용(+$0.0005)과 지연(+1.8초)만 유의하게 늘었다. 이 평가셋에서 Judge가 올린 품질은 측정되지 않았다.
- **캐스케이드.** 비용 −$0.0030만 유의하다. 이 행은 캐스케이드와 캐시를 함께 켠 구성이지만 비교에 쓴 반복에서는 캐시 적중이 0회(cold)이므로 효과는 캐스케이드로 읽는다. 지연은 −0.1초 [−0.6, +0.3]로 차이가 있다고 말할 수 없다. 이전 판의 지연 감소(−0.8초 유의)는 캐시 오염이었다. 품질은 차이가 있다고 말할 수 없지만, 어구 포함(−5%p)과 통과율(−4%p)의 점추정이 모두 음수이고 통과율은 dev에서도 같은 방향이다(dev 통과 −3 [−10, +1]). dev 어구는 −1%p [−13, +12]로 거의 같다. 품질 손실이 없다고 단정하지 않는다. 어구 포함에서 최대 19%p 하락까지는 이 데이터로 배제하지 못한다.
- **v2 보완.** 혼입 −24%p만 유의하다. 누락, 어구 포함, 통과율은 차이가 있다고 말할 수 없고 비용과 지연도 차이가 없다. 보완 4건이 한 구성에 묶여 있어 개별 기여는 분리하지 않았다. 혼입 감소는 5절에서 `min_score`에 귀속한다.
- **v2 위에 비용·런타임.** 비용 −$0.0029와 지연 −0.4초가 유의하고 품질은 차이가 있다고 말할 수 없다. 이 구성은 캐스케이드, 캐시, 비동기 I/O, 도구 부분 실패 허용을 한꺼번에 켜므로 지연 감소를 하나로 귀속할 수 없다. 캐시는 cold 반복이라 지연 감소의 원인에서 빠진다. 지연 감소 폭(−0.4초)은 이전 판(−1.1초)의 3분의 1 수준이다. dev에서는 final이 v2보다 어구 포함이 10%p 낮았고 유의했다(`results/stats_dev.json`, −10 [−19, −1]. 이전 판 −13 [−23, −4]). holdout에서는 이 차이가 나타나지 않았다.
- **전체.** 품질 5지표는 모두 유의하게 좋아졌고 질의당 비용은 유의하게 줄었다. 지연은 질의당 +1.8초 유의하게 늘었다. base보다 느려진 것이며, final에 이르는 행(RAG +0.4, Judge +1.8, v2 +0.1, 비용·런타임 −0.4)의 지연 변화를 더하면 이 값과 같다. 즉 RAG 검색과 Judge가 더한 지연을 v2 위 최적화가 일부만 되돌렸다. p95는 8.3초에서 10.7초다.

## 3. 운영 지표 해석

세 지표는 `eval/extra_metrics.py`가 저장된 `rows`에서 계산한다. 재실행 없이 사후 계산한 값이다.

| 지표 | 정의 | 운영에서 뜻하는 것 |
|---|---|---|
| 정답 런북 누락 | 장애 경로로 처리했고 정답 런북이 있는 질의 중, 정답 런북이 근거에 하나도 투입되지 않은 비율 | 맞는 조치를 권고하지 못한다 |
| 무관 런북 혼입 | 장애 경로로 처리한 질의 중, 정답 밖의 런북이 근거에 섞인 비율. 정답이 없는 질의에 런북을 넣은 경우도 센다 | 잘못된 조치가 권고에 섞인다 |
| 장애 1건당 비용 | 해당 반복의 전체 질의 비용 / 장애 경로로 처리된 질의 수 | 장애 한 건을 처리하는 평균 API 비용 |

- 복합 장애(정답 런북 2개)는 하나만 넣어도 누락이 아니다.
- 혼입은 심각도를 구분하지 않는다. 정답 런북과 함께 무관한 런북이 하나 더 들어가도 혼입으로 센다.
- 장애 경로 질의 수는 구성마다 29.0~29.7건이다. 라우터가 일부 반복에서 형식 제약 질의를 장애로 보낸 경우가 있다 (base의 Q46 2회, rag_judge_cost‡의 Q43 1회, rag_judge_v2의 Q43 1회·Q46 1회, final‡의 Q43 1회).

**누락.** base는 장애 답의 56%가 정답 런북을 근거에 넣지 못했다. 원본이 질의가 아니라 모니터링 알림 문구의 키워드로 런북을 고르기 때문이다. RAG 이후 9%로 줄었다. 남은 9%는 Q30("야간 정산 배치가 겹쳐서 … 서버 하나가 계속 풀로드")과 Q36("특정 서버 한 대에서만 요청이 유난히 오래 걸리는 것 같아요")이다. 둘 다 질의를 자기 말로 푼 문항이고 RAG 1위가 다른 런북(disk-full)이었다. 3회 반복에서 매번 같았다.

**혼입.** RAG는 혼입을 거의 줄이지 못했다(65% → 59%, 유의하지 않음). v2에서 35%로 줄었다. 혼입이 남는 이유는 두 가지다. 정답 없는 질의(미등록·모호)에 가장 비슷한 런북을 넣는 경우, 정답 런북 옆에 1위 점수에서 0.05 이내의 다른 런북이 함께 투입되는 경우다 (`margin: 0.05`, `src/ext/rag.py`). v2 이후 남은 혼입 34%의 구성은 반복당 평균 10.0건 중 정답 없는 질의 2건(Q53, Q57), 정답 있는 질의의 덧붙은 런북 8.0건이다.

**건당 비용.** 단위는 USD다.

| 비교 | 건당 비용 | 변화 |
|---|---|---|
| base → rag | 0.00343 → 0.00397 | +16% |
| rag → rag_judge | 0.00397 → 0.00464 | +17% |
| rag_judge → rag_judge_cost‡ | 0.00464 → 0.00086 | −81% |
| rag_judge → rag_judge_v2 | 0.00464 → 0.00415 | −11% (2절에서 유의하지 않음) |
| rag_judge_v2 → final‡ | 0.00415 → 0.00064 | −85% |
| base → final‡ | 0.00343 → 0.00064 | −81% |

변화율은 위 평균값끼리의 비다. 유의성은 2절 질의당 비용 표로 판단한다.

cost‡와 final‡의 건당 비용은 cold 반복(1·3회차, 캐시 적중 0회)만의 평균이다. 이전 판은 캐시가 적중한 2회차를 평균에 넣어 cost $0.00087, final $0.00058(base 대비 −83%)이었다. 2회차를 빼면 cost $0.00086, final $0.00064이고 base 대비 final은 −81%다. 결론은 같고 final의 절감폭만 2%p 작아졌다. 반복 2회라 final‡ 건당 비용의 ±는 $0.00101로 평균보다 크다(1절).

## 4. 편향 검증

평가셋이 특정 방식에 유리하게 짜였는지 두 가지로 본다. 출처는 `python -m eval.extra_metrics`(`design_note`, `split`별 Recall@1)와 `summary.by_split.{dev,holdout}.mean["recall@1"]`이다.

**aligned vs paraphrased.** normal 문항은 aligned(증상과 일치하는 알람을 가진 시스템을 지목한 문항)와 paraphrased(운영자가 자기 말로 증상을 풀어 쓴 문항)로 나뉜다. holdout은 9건씩, dev는 6건씩이다.

| 구성 | holdout aligned (n=9) | holdout paraphrased (n=9) | 전체 aligned (n=15) | 전체 paraphrased (n=15) |
|---|---|---|---|---|
| base | 78% | 11% | 73% | 13% |
| rag | 100% | 33% | 100% | 60% |
| final | 100% | 33% | 100% | 60% |

- 질의 한 건이 holdout에서 11%p다. 이 표의 차이는 크지만 표본은 작다.
- base의 aligned 78%는 키워드 규칙이 알림 문구와 겹치는 질의에서만 맞는다는 뜻이다. 질의를 자기 말로 풀면 11%로 떨어진다. 평가셋이 paraphrased를 절반 포함해 base에 불리한 면이 있다는 점은 인정해야 한다. 다만 holdout에서 RAG의 개선폭은 두 부분집합에서 같다(aligned +22%p, paraphrased +22%p).
- RAG도 paraphrased에서는 holdout 9건 중 3건만 1위로 맞췄다. 6개 런북에 작은 임베딩 모델(text-embedding-3-small)로 한 검색이 질의를 자기 말로 풀면 약해진다.

**dev → holdout.** 기준값을 조정한 dev에서의 수치가 holdout에서 얼마나 유지되는지 본다.

| 구성 | dev Recall@1 | holdout Recall@1 | 차이 |
|---|---|---|---|
| base | 36% | 33% | −3%p |
| rag | 72% | 52% | −20%p |
| final‡ | 72% | 54% | −18%p |

- RAG의 검색 성능은 holdout에서 20%p 낮다. dev에서 RAG는 paraphrased 6건을 모두 맞췄고(100%) holdout에서는 9건 중 3건만 맞췄다. dev 24건만 봤다면 RAG를 과대평가했을 것이다.
- 반면 답변 쪽 지표는 덜 흔들렸다. rag의 어구 포함은 dev 87% → holdout 81%, Judge 통과는 96% → 97%다.
- Recall@1에는 라우터가 형식 제약 질의 5건을 chat으로 보내 검색이 일어나지 않은 경우가 들어 있다. 장애 경로로 간 질의만 보면 holdout Recall@1은 base 39%, rag 63%, final 64%다 (`recall@1|incident`). 이 라우팅은 개선 대상이 아니었고 구성 간에 같다.
- holdout 문항 작성 시점은 v1 실측(10:45 종료) 뒤다. `eval/queries.yaml` 머리말은 문항을 측정 결과를 보기 전에 작성했다고 적는다. 문항을 쓴 사람이 v1의 약점(미등록·모호 질의)을 알고 있었으므로 그런 문항이 holdout에 포함됐을 가능성은 배제하지 못한다.

## 5. v2 보완

v1 실측에서 찾은 약점과 holdout에서 확인한 결과다. 구성: `eval/configs/rag_judge_v2.yaml`, 구현: `src/ext/rag.py`, `src/ext/judge.py`, `src/ext/factcheck.py`, `src/ext/graph_ext.py`.

| v1에서 찾은 약점 | v2 조치 | holdout 결과 |
|---|---|---|
| 미등록·모호 질의에도 런북을 1~3개 넣는다 | `rag.min_score: 0.3236` 미만이면 런북을 넣지 않고 '일치 런북 없음' 안내를 근거에 넣는다 | 혼입 59% → 35% (−24%p [−41, −10], 유의) |
| Judge가 근거에 없는 절차를 요구하며 반려하고, 재작성 답이 무관한 절차를 섞었다 | Judge v2: 근거 밖 요구 금지, `fixable` 판정. `fixable=false`면 재작성하지 않는다 | 재작성 2.0 → 0회/반복. 품질은 차이가 있다고 말할 수 없음 |
| Judge가 근거에 없는 수치를 못 잡을 수 있다 | `judge.factcheck`: 답변 수치를 코드로 근거와 대조해 Judge 호출 없이 반려 | 효과 확인 못 함 (아래) |
| 질의에 등록 시스템명이 없어 auth-service로 폴백 조회한 사실이 답에 안 나온다 | `rag.notices`: 폴백 사실을 근거에 명시 | 별도 지표가 없어 측정하지 않음 |
| 동기 HTTP 호출이 이벤트 루프를 막고, 도구 하나가 실패하면 질의 전체가 실패한다 | `runtime.async_io`, `runtime.tolerant_research` | 6절 벤치: 모의 LLM·fake 백엔드로 메커니즘만 확인했고 실제 API 지연·실제 장애는 측정하지 않음 |

**혼입 감소의 구성.** 혼입은 근거에 투입한 런북(`fed_runbooks`)으로만 계산한다(`eval/extra_metrics.py`의 `_wrong`). Judge, 수치 검증, 안내 문구는 투입 런북을 바꾸지 못하므로 이 지표의 감소는 `min_score`에서만 나올 수 있다. 반복당 혼입 건수는 rag 17.0건에서 v2 10.3건으로 6.7건 줄었다 (`rows`에서 계산).

- 정답 없는 질의 4.0건: 장애 경로로 간 정답 없는 질의 6건 중 런북이 투입된 수가 6 → 2건이 됐다.
- Q30, Q36에서 2.0건: 1위가 오답이고 점수가 기준 미만(0.3106, 0.3048)이어서 오답 런북 대신 안내가 들어갔다. 이 두 질의는 RAG에서도 정답을 못 찾은 누락이다.
- 나머지 0.7건은 정답 옆에 덧붙던 런북이 기준 미만으로 빠진 경우와 라우팅 변동이다.

혼입 감소의 약 3분의 1은 이미 틀린 질의에서 오답 런북을 '없음'으로 바꾼 것이고, 정답을 찾은 질의의 품질이 올랐다는 뜻이 아니다.

**누락 9% → 10%.** 점추정이 오른 것은 `min_score`가 정답을 잘라서가 아니다. 누락 질의는 rag와 같은 Q30, Q36이고, 추가로 v2의 2회차에서 형식 제약 질의 Q46("DB 프라이머리 장애 시 첫 조치를 100자 이내로")이 장애 경로로 가서 1위가 disk-full(0.3789)이었다. 라우터 변동 1건이다. holdout에서 정답이 1위인데 기준 미만인 질의는 0건이다. rag_judge는 8.7%, v2는 9.8%이며 stats에서 차이가 있다고 말할 수 없다(0 [0, 0]).

**`min_score`의 취약성.** 기준값 0.3236은 dev 24건만으로 정했다 (`results/calibrate_rag.json`). dev에서는 정답 있는 질의의 최저 점수 0.3248과 정답 없는 질의의 최고 점수 0.3225 사이에 기준을 놓았고, 그 간격이 0.0023이다. 이 값은 dev에 맞춘 것이다.

holdout에서는 점수 범위가 겹친다. 1위가 정답인 17건의 점수는 0.345~0.593이고, 정답 없는 질의로 장애 경로에 간 6건은 0.235~0.382다. 미등록 질의 Q53(0.3815)과 모호 질의 Q57(0.3426)이 기준을 넘어 런북이 투입됐고, Q53은 정답 1위 17건 중 3건(0.345~0.379)보다 점수가 높다. 6건 중 4건만 걸러졌다. 어떤 기준값도 이 6건을 모두 거르려면 정답 일부를 잘라야 한다. 이 점수는 사후에 읽은 것이며 기준값 조정에 쓰지 않았다.

**수치 검증.** 근거에 없는 수치가 든 답의 비율은 base를 포함한 다른 구성에서 모두 0%였다. rag_judge_cost‡만 72회 중 1회(Q33, 1회차, 근거에 없는 수치 20.0)다. 기준선이 0%에 가까워 `factcheck`의 효과는 이 평가셋에서 측정되지 않는다. final‡에서 코드 검증이 반려한 것은 72회 중 1회이고 역시 Q33 1회차다(근거에 없는 수치 20.0을 반려하고 재작성, 재작성 답은 통과). 같은 질의·회차에서 cost 구성은 수치가 그대로 나갔고 final은 걸러졌으나, 두 구성은 별개의 실행이라 한 건으로 효과를 주장하지 않는다.

**Judge v2가 하는 일.** v2의 holdout 재작성은 0회다. 그러나 Judge가 근거 밖 요구로 판정해 재작성을 생략한 경우가 108회 중 13회 있었다. 이 답은 그대로 나갔다. v2 Judge는 답을 고치는 장치가 아니라 반려를 해도 재작성하지 않는 쪽으로 비용을 막는 장치로 작동했다.

## 6. 운영 안정성 (벤치)

벤치는 3종이다. 실제 API로 잰 것은 캐시 벤치뿐이다. 동시성과 장애 벤치는 API 지출 한도와 무관하게 돌릴 수 있도록 LLM을 모의 백엔드로 바꿔 코드 경로만 확인했다. 따라서 둘 다 실제 API 지연이나 실제 장애에서의 성능이 아니다. 7구성 비교(1~5절)와 달리 이 절의 수치는 구성 간 품질 비교에 쓰지 않는다.

### 6.1 캐시 벤치 (실제 API)

`results/cache_bench_latest.json`. final 구성, 60건을 같은 프로세스에서 순서대로 두 번 돌렸다. 2회차는 1회차와 같은 질의이므로 캐시에는 가장 유리한 조건이다. 캐시 키 정규화는 대소문자·공백·문장부호만 흡수한다.

| | 1회차 | 2회차 |
|---|---|---|
| 캐시 적중 / 조회 | 0 / 160 | 112 / 160 (70%) |
| 지연 p50 | 7.9초 | 5.6초 (−29%) |
| 비용 (60건 합계, 추정) | $0.02719 | $0.02332 (−14%) |
| 입력 / 출력 토큰 | 97,525 / 21,452 | 78,235 / 19,462 |

- 미스 18건은 모두 2회차 앞쪽 Q01~Q18이고 Q19 이후 42건은 전 조회가 적중했다. 앞쪽 질의의 캐시가 TTL(600초)로 만료된 것으로 보이나, 1회차 질의별 지연의 합이 441초라 합만으로는 600초 초과가 설명되지 않는다. 만료 시각을 기록하지 않아 확인하지 못했다.
- 2회차에서 전 조회가 적중한 42건의 p50은 5.5초, 미스가 있던 18건은 8.0초다.
- 캐시 대상은 route·plan·질의 임베딩뿐이고 작성·Judge 호출은 캐시하지 않는다. 이 세 단계가 cold 비용에서 차지하는 비중을 현재 `rows[].llm_calls`(1·3회차 120회, 단가 x 토큰)로 다시 계산하면 final $0.01139 / $0.05849 = 19.5%, rag_judge_cost $0.01152 / $0.11403 = 10.1%다. 적중 70% x 19.5% = 13.6%는 관측한 −14%와 맞는다. 이전 문서의 "약 8%"는 v1(dev 24건) 수치이고 현재 rows에서는 재현되지 않는다.
- 효과 범위는 같은 질의를 다시 물을 때로 한정된다. 7구성 비교에서는 질의가 겹치지 않아 적중이 0회였고 그래서 캐시 효과는 1~5절에 나타나지 않는다.

### 6.2 동시성 벤치 (모의 LLM, 실제 API 아님)

`results/concurrency_bench_simulated_latest.json`. 원본 노드는 `async`이지만 그 안의 LLM 호출이 동기라서 이벤트 루프를 막는다. `runtime.async_io`를 끈 final과 켠 final을 비교해 그 효과만 본다. 백엔드는 `fake_slow`다. LLM 호출마다 동기 지연 0.5초(작성은 1.0초)를 `time.sleep`으로 넣었고 비용은 0이다. 캐시는 껐다. 질의는 dev normal 앞 N건을 같은 이벤트 루프에서 동시에 실행했다.

| 동시 질의 N | 벽시계 시간 sync / async_io | 배율 | 평균 질의 지연 sync / async_io | 처리량 (질의/초) sync / async_io |
|---|---|---|---|---|
| 1 | 4.67초 / 4.64초 | 1.0배 | 4.67초 / 4.64초 | 0.21 / 0.22 |
| 3 | 9.70초 / 4.75초 | 2.0배 | 7.14초 / 3.51초 | 0.31 / 0.63 |
| 5 | 14.83초 / 4.68초 | 3.2배 | 9.72초 / 3.21초 | 0.34 / 1.07 |
| 10 | 19.93초 / 4.70초 | 4.2배 | 11.73초 / 2.14초 | 0.50 / 2.13 |

- sync는 N이 늘수록 벽시계 시간이 4.7초에서 19.9초로 늘고, async_io는 4.6~4.8초로 거의 그대로다. 블로킹 호출이 이벤트 루프를 막아 동시 요청이 줄을 선다는 메커니즘이 모의 조건에서 확인됐다. sync의 증가가 N에 비례하지는 않았고 이유는 확인하지 않았다.
- 이 수치는 지연을 일정(0.5초)하게 둔 모의 값이다. 실제 API에서는 호출 지연이 흔들리고 API 속도 제한(429)이 걸리며 스레드 풀 크기도 영향을 준다. 이 벤치로는 실제 환경의 처리량 배율을 말할 수 없다.

### 6.3 장애 주입 벤치 (fake 백엔드)

`results/fault_bench_fake_latest.json`. 백엔드는 `fake`다. 모든 질의를 장애 경로로 강제하고, `get_monitoring_status` 호출의 30%를 일부러 실패시켰다(seed 7, 같은 질의·대상이면 같은 호출이 실패한다). 질의는 normal·composite 38건, 캐시는 껐다. "완주"는 예외 없이 답을 반환한 것이다.

| 변형 | 완주 (38건 중) | 실패가 걸린 21건 중 완주 |
|---|---|---|
| base | 17 | 0 |
| final_no_tolerance (final에서 `tolerant_research`만 끔) | 17 | 0 |
| final | 38 | 21 |

- 원본 `research_node`는 `asyncio.gather`로 태스크를 묶어 하나라도 영구 실패하면 질의 전체가 예외로 끝난다. `tolerant_research`를 켜면 실패한 태스크만 '조회 실패'로 근거에 남기고 나머지로 답한다. 표에서 base와 final_no_tolerance가 같고 final만 21건을 모두 완주한 것은 이 설정 하나의 효과다. final에서 주입된 실패 호출은 24건이다.
- fake LLM이라 답의 품질은 보지 않았다. 완주 여부만 측정한 것이고, '조회 실패'를 근거에 두고 쓴 답이 운영에서 쓸 만한지는 이 벤치로 판단하지 못한다.
- 모니터링 도구 한 종류의 실패만 주입했다. 런북 검색이나 LLM 호출의 실패는 주입하지 않았다.

### 6.4 재시도 정책

OpenAI 429가 난 것을 계기로 재시도 정책을 바꿨다(606af8e: Retry-After 존중, 최대 60초 대기, 7회 재시도, 질의별 재시도 횟수 `api_retries` 기록). 이 변경은 이후 실행에만 적용된다. 이 문서의 7구성 실측은 변경 전 실행이고 오류 0이었다. 당시에는 재시도 횟수를 기록하지 않아 결과 파일의 `api_retries` 0은 의미가 없다.

## 7. 평가자 검증

**사람 라벨은 아직 없다.** `eval/human_labels.yaml`이 없어 사람 vs 평가 Judge 일치율은 산출하지 않았다. 표본 20건(카테고리 층화 무작위, seed 20261021)은 `eval/human_sample_ids.txt`, 절차는 `docs/라벨링_가이드.md`에 있다. Q01은 첫 가이드에 예시 판정이 실려 라벨러에게 노출됐으므로 일치도 계산에서 뺀다(19건, `eval/human_exclude.txt`, 사유 `eval/human_sample_note.txt`). 라벨은 `scripts/label.py`로 입력하고 `python -m eval.agreement`로 일치율을 낸다. 그 전에는 "평가 Judge를 사람이 검증했다"고 쓸 수 없다.

**독립 평가자(Claude)와의 일치도. 사람 라벨이 아니다.** `eval/claude_labels.yaml`은 Claude 서브에이전트(파일의 `rater` 필드: claude-opus-5.5, 블라인드)가 base 구성 1회차 답변 60건을 평가 Judge의 판정을 가린 파일만 보고 지표별 Pass/Fail로 채점한 것이다. 평가 Judge(gpt-4o)와 다른 모델 계열이라 "Judge와 다른 평가자의 일치도"를 재는 데 쓴다. 비교 대상은 같은 60건에 대한 평가 Judge 판정이다 (`python -m eval.agreement --labels eval/claude_labels.yaml`).

| 지표 | n | 일치율 | kappa | 평가자 Pass·Judge Pass | Pass·Fail | Fail·Pass | Fail·Fail | Judge 관대도 | Judge 엄격도 |
|---|---|---|---|---|---|---|---|---|---|
| relevance | 60 | 73% | 0.44 | 32 | 0 | 16 | 12 | 57% | 0% |
| completeness | 60 | 78% | 0.02 | 46 | 8 | 5 | 1 | 83% | 15% |
| domain_appropriateness | 60 | 55% | 0.25 | 17 | 0 | 27 | 16 | 63% | 0% |
| clarity | 60 | 95% | 0.37 | 56 | 1 | 2 | 1 | 67% | 2% |
| overall (4지표 중 3개 이상 Pass) | 60 | 70% | 0.39 | 30 | 1 | 17 | 12 | 59% | 3% |

- 열 순서는 평가자 판정·Judge 판정이다 (Pass·Fail = 평가자 Pass, Judge Fail). Judge 관대도 = P(Judge Pass | 평가자 Fail), 엄격도 = P(Judge Fail | 평가자 Pass).
- overall에서 Judge는 47/60(78%)을 통과시켰고 Claude는 31/60(52%)을 통과시켰다. 평가자가 Fail로 본 29건 중 17건(59%)을 Judge가 통과시켰고, 평가자가 Pass로 본 31건 중 Judge가 떨어뜨린 것은 1건뿐이다. 불일치는 지표 x 질의 240쌍 중 59쌍이고 50쌍이 Judge 관대, 9쌍이 Judge 엄격이다.
- 관대함은 domain_appropriateness(27쌍)와 relevance(16쌍)에 몰려 있다. 평가자는 런북이 없는데 없다고 밝히지 않은 답, 무관한 런북 절차를 섞은 답, 일반론을 추측한 답을 Fail로 봤고 Judge는 Pass로 뒀다. 카테고리별 불일치율은 normal 16%, constrained 31%, unregistered 32%, composite 34%, ambiguous 36%다. 근거가 약하거나 비어 있는 질의에서 Judge가 더 관대하다는 뜻이며 아래 포화 관찰과 같은 방향이다.
- completeness는 일치율 78%인데 kappa가 0.02다. 두 평가자 모두 대부분 Pass를 줘서 우연 일치와 구분되지 않는다. 이 지표는 이 표본에서 변별력이 없다.
- 평가자 Pass이고 Judge Fail인 9쌍은 completeness 8건(Q01, Q06, Q08, Q14, Q25, Q32, Q53, Q55)과 clarity 1건(Q13, 답이 50자 제약 초과라는 Judge 사유)이다.

이 결과를 읽는 한계는 다음과 같다.

- Claude는 사람이 아니다. 같은 LLM이 채점한 것이고, 런북 부재 미고지를 Fail로 보는 식의 기준이 정답이라는 근거는 없다. 일치율이 낮다는 것은 Judge가 틀렸다는 증명이 아니라 Judge 통과율의 절대값을 그대로 믿기 어렵다는 신호다.
- 평가자가 1명이고 1회 채점이다. 평가자 내 일관성은 재지 않았다.
- base 구성의 1회차 답변만 비교했다. rag 이후 구성에서 일치도가 어떤지는 측정하지 않았다.
- 사람 라벨이 들어오면 사람 vs Judge, 사람 vs Claude, Claude vs Judge 세 일치도를 같은 명령으로 낸다.

**평가 Judge의 포화.** 위 일치도와 별개로, 저장된 `rows`에서 평가 Judge(gpt-4o)가 관대했다는 증거를 확인했다. 아래는 rag 구성의 holdout 108회(36건 x 3회)다.

| 관찰 | 값 | 근거 |
|---|---|---|
| 평가 Judge 통과율 | 105/108 (97%) | `rows[].judge_passed`. 실패 3회는 모두 Q55(미등록) |
| 런북 핵심 어구 포함률 (Judge 무관) | 81% | `must_phrase_rate`, 어구 전부 포함은 73% |
| 어구를 일부 누락한 답 18회 중 Judge가 통과시킨 것 | 18/18 | 어구가 지정된 66회 중 |
| 정답 런북이 근거에 없는 답 중 Judge 통과 | 21/21 | 형식 제약 질의 chat 15회, Q30·Q36 6회 |
| 근거가 비어 있는 chat 답의 completeness | 21/21 Pass | Q43~47, Q56, Q59. 지어낸 게 없다는 판정 |

- 평가 Judge는 근거에 정답 런북이 없거나 근거 자체가 비어 있어도 통과시켰다. rag에서 통과율이 97%로 포화돼 구성 간 차이를 거의 못 보여준다. 1절에서 어구 포함 같은 결정적 지표를 함께 쓴 이유다.
- base에서는 이 관대함이 덜했다. 정답 누락 53회 중 35회를 통과시키고 18회를 실패시켰다. 틀린 런북이 붙은 답을 일부는 잡는다. 어구를 일부 누락한 47회 중에서는 31회를 통과시켰다.
- 평가 Judge와 write 모델이 모두 gpt-4o인 구성(base, rag, judge, rag_judge, rag_judge_v2)이 있다. 같은 모델이 쓴 답을 같은 모델이 채점하는 편향이 있을 수 있다. 이를 직접 측정하지 않았다.
- 어구 포함률은 표현만 바꾼 경우(예: failover → 페일오버)를 놓치는 하한 지표다. 어구는 측정 전에 정답 런북 본문에서 뽑았다 (`eval/answer_metrics.py`).

## 8. 한계

- **표본.** holdout 36건이다. 질의 1건이 2.8%p, 정답 런북이 있는 28건 기준으로 3.6%p다. 어구는 22건에만 지정돼 있다. 반복(2~3회)은 실행 변동을 줄여 줄 뿐 질의 수를 늘리지 못한다. bootstrap CI는 질의 변동을 반영하지만 질의 세트가 하나다.
- **다중 비교.** 비교 49개에 보정이 없다. 하한이 0에 가까운 유의 결과(예: RAG 단독의 지연 +0.4초 [+0.1, +0.6])는 약하게 읽는다.
- **평가 Judge 포화, 사람 검증 없음.** 7절 참조. Judge 통과율만으로는 구성을 가를 수 없다. 사람 라벨 일치율은 아직 없다. 독립 평가자 일치도(overall 70%, kappa 0.39)는 Claude와 잰 것이고 사람이 검증한 것이 아니다.
- **지연의 측정 조건.** 7구성 프로세스를 동시에 돌리고 구성당 worker 3개를 썼다 (`scripts/run_all.sh`). 지연은 이 부하에서 쟀으므로 구성 간 상대 비교로만 쓴다. 단일 요청의 지연이 아니다.
- **API 지출 한도와 cold 재측정 불가.** rag_judge_cost와 final의 2회차가 캐시 오염으로 빠졌고, 반복을 다시 재려 했으나 실측에 쓴 OpenAI 프로젝트(개인 프로젝트, 월 한도 $10)가 지출 한도(`project_spend_limit_exceeded`)에 걸려 하지 못했다. 이후 API를 쓰는 추가 실측도 같은 이유로 막혀 있다.
- **두 구성은 반복 2회다.** rag_judge_cost와 final의 반복 간 95% CI는 t(df=1)=12.7을 써서 매우 넓다(예: Recall@1 ±23%p, Judge 통과 ±18%p). 이 둘이 낀 bootstrap 비교는 질의별 값이 2회 평균이라 3회 평균보다 실행 변동이 더 남아 있다. 이 구성들의 반복 간 ±로 구성을 가르지 않는다.
- **벤치 2종은 모의다.** 동시성 벤치는 지연을 고정한 모의 LLM(`fake_slow`), 장애 주입 벤치는 `fake` 백엔드로 쟀다. 코드 경로의 동작만 확인했고 실제 API 지연·처리량·실제 장애에서의 답 품질은 측정하지 않았다. 실제 API로 잰 것은 캐시 벤치뿐이고 그것도 같은 질의를 반복한 최선의 조건이다.
- **재시도 정책 변경(606af8e)은 이후 실행에만 적용된다.** 이 문서의 수치는 변경 전 실행이다.
- **비용은 추정이다.** 공개 단가 x 실측 토큰이다. 평가 Judge 호출과 런북 색인 임베딩을 뺐고 실제 청구액이 아니다.
- **v2는 묶음이다.** 최소 유사도, Judge v2, 수치 검증, 안내 문구를 한 구성으로 켰다. 혼입 감소는 논리상 `min_score`에 귀속하지만 나머지의 개별 효과는 분리하지 않았다.
- **`min_score`는 dev에 맞췄다.** 간격 0.0023이고 holdout에서 범위가 겹쳤다. 다른 질의 분포에서는 기준값을 다시 정해야 한다.
- **라우터는 범위 밖이다.** 형식 제약 질의(holdout 5건)는 대부분 chat으로 가서 검색이 일어나지 않는다. Recall@1에 그만큼 반영돼 있다. 라우팅은 반복마다 흔들렸다 (Q43, Q46).
- **혼입은 심각도를 구분하지 않는다.** 정답 옆에 무관한 런북이 하나 붙은 경우와 정답 없이 오답만 들어간 경우를 같게 센다.
- **dev와 holdout의 격차.** RAG의 Recall@1이 dev 72%, holdout 52%다. 실제 질의 분포에서 더 낮을 수 있다. 질의는 프로젝트에서 작성한 것이고 운영 로그가 아니다.
- **한 모델 계열.** OpenAI의 gpt-4o, gpt-4o-mini, text-embedding-3-small만 썼다. 다른 계열에서 같은 결론이 나오는지 보지 않았다.
- **환경.** 런북은 6종이고 모니터링 값은 호출마다 무작위로 흔들리는 목업이다 (`src/mcp_server.py`). 실제 운영 환경이 아니다.
- **dev에서만 나타난 품질 하락.** final은 dev에서 v2보다 어구 포함이 10%p 낮았다(−10 [−19, −1], 유의. dev 88% → 78%). holdout에서는 나타나지 않았지만 원인을 밝히지 못했다.
