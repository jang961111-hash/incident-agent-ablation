# 글로벌 AI 인시던트 대응(AI SRE / AIOps) 실태 현황

- 조사일(모든 출처 접속일): **2026-10-22**
- 조사 방법: WebSearch로 후보를 찾은 뒤, 가능한 한 **공식 페이지(보도자료, 공식 문서, 체인지로그, 공식 블로그)를 WebFetch로 직접 열어** 내용을 확인했다.
- 표기 규칙
  - **[벤더 주장]**: 회사가 스스로 발표한 수치다. 측정 방법이 공개되지 않았고 독립 검증도 없다.
  - **[미검증]**: 공식 페이지가 403/502 등으로 열리지 않아 2차 출처(언론, 검색 요약)로만 확인한 내용이다.
  - 국가는 본사 소재지 기준의 일반 공개 정보로, 이번 조사에서 출처를 따로 대조하지 않았다.

## 2. 우리 프로젝트와 연결되는 인사이트

### 인사이트 1. 업계 표준 근거는 "텔레메트리 + 과거 인시던트 + 런북"이다. 런북 RAG를 택한 방향이 이 흐름과 맞다

- 런북을 직접 근거로 쓰는 곳: AWS DevOps Agent는 런북을 agent skills로 encode한다. Azure SRE Agent는 승인된 런북, skills를 쓰고 Review 모드에서 런북 맥락을 첨부한다. Gemini Cloud Assist는 절차형 런북을 쓴다. Datadog 보도자료도 런북을 분석 대상으로 꼽는다.
- 과거 인시던트를 근거로 쓰는 곳: PagerDuty("memory"), incident.io, Rootly, Komodor(과거 조사 흐름), AWS(과거 인시던트 패턴), Azure(과거 조사 맥락 보존).
- **우리 프로젝트와의 연결**: 키워드 규칙 대신 RAG로 런북 6종 중 하나를 고르는 개선은 업계가 쓰는 근거 방식과 같은 축이다. 상용 제품은 여기에 "유사 과거 인시던트 검색"을 더한다. 이 점은 한계와 확장 방향으로 적을 수 있다.
- 근거 출처: AWS 문서, Azure 개요 문서, Google 조사 문서, Datadog 보도자료, PagerDuty Spring 26 블로그, incident.io 블로그, Rootly AI SRE 페이지, Help Net Security(Komodor)

### 인사이트 2. 선두 업체는 "고정 라벨셋 + LLM 판정 + 회귀 측정"으로 에이전트를 평가한다. 우리의 고정 평가셋, LLM-as-a-Judge, Ablation과 같은 방식이다

- Datadog은 수백 개 팀이 라벨링한 실제 인시던트로 벤치마크를 만들었다. LLM judge가 여러 기준으로 채점하고, 그 점수를 사람 판정에 맞춰(align) pass/fail을 정한다(구축기 블로그 2026-01-12).
- Datadog 평가 플랫폼 블로그(2026-04-07)에는 이런 사례가 나온다. 알림의 서비스명을 초기 맥락에 넣는 기능이 일부 조사는 개선했지만 다른 조사에서는 무관한 신호를 늘려 **회귀**를 일으켰다. 대표 사례가 적은 내부 테스트로는 이를 잡지 못했다. 이후 Datadog은 무관한 구성요소를 **방해 신호(distractor)**로 주입하지 않으면 실제보다 점수가 좋게 나온다고 밝혔다. 또 신호 재구성을 넓혀 라벨을 다시 만들자 통과율이 약 11% 내려갔다.
- Traversal 가이드는 과거 주요 인시던트 약 10건으로 **백테스트**하고, 사전에 합의한 등급형 스코어카드(정확한 RCA 100% ~ 오도하는 RCA 0%)로 채점하라고 권한다. 마지막에는 처음 보는 실운영 인시던트로 검증하라고 한다.
- RCACopilot은 1년치 실제 인시던트로 Micro-F1 0.766을 보고했다. 연구계도 고정 데이터셋 지표를 쓴다.
- **우리 프로젝트와의 연결**: "평가셋 고정 → 구성별 실행 → 기여도 분해" 절차는 업계 선두의 내부 관행과 같다. Datadog의 회귀 사례는 기능 하나를 켜고 끄며 효과를 측정하는 Ablation이 왜 필요한지 보여 준다. 시사점은 두 가지다. ① Judge 점수를 사람 라벨과 대조하는 정합성(calibration) 점검, ② 평가 입력에 방해 신호를 섞는 강건성 시험. 두 가지 모두 한계, 개선안으로 언급할 만하다.
- 근거 출처: Datadog 구축기, 평가 플랫폼 블로그, Traversal 평가 가이드, RCACopilot 논문

### 인사이트 3. 공개 수치는 대부분 "최대 X%"이고 방법론이 없다. 구성요소별 기여도를 공개한 곳은 거의 없다

- 확인한 벤더 주장: incident.io, Resolve "downtime/MTTR 최대 80%", Datadog "TTR 최대 95% 감소", PagerDuty "alert noise 91% 감소", New Relic "25% faster", Rootly "10x faster", Resolve "5x faster MTTR", Traversal ">90% accuracy", Cleric "역량 20~30%"(미검증)
- 대부분 "up to"가 붙은 최대치이거나 고객 사례 1건이다. 표본, 기준선, 측정 방법은 공개되지 않았다.
- 예외에 가까운 사례가 Dynatrace다. "결정론적 에이전트가 있을 때와 없을 때"를 비교해 "최대 12배 더 자주, 3배 빠르게, 절반 비용"이라고 밝혔다. 형식은 Ablation에 가깝지만 과제셋, 표본 수, 방법론은 비공개다.
- AWS는 GA 공지와 공식 문서에 정량 수치를 싣지 않았다("hours to minutes"만 있음). 2차 매체가 인용한 75%, 94% 수치는 공식 페이지에서 확인하지 못했다.
- **우리 프로젝트와의 연결**: 우리는 구성요소(RAG, Judge, 캐스케이드, 비동기, 도구 장애 내성)마다 on/off 구성을 돌린다. 그리고 모든 수치를 `results/` 실행 결과로 뒷받침한다. 이 점이 차별점이다. 발표에서는 "업계는 최종 효과(최대치)만 공개하고, 우리는 기여도를 분해해 공개한다"고 대비시킬 수 있다.
- 근거 출처: 표 1-A~1-D의 각 수치 출처, Dynatrace 보도자료, AWS GA 공지

### 인사이트 4. 자동 조치(remediation)는 사람 승인을 기본값으로 둔다. 자율 실행은 설정으로만 연다

- Azure SRE Agent에는 run mode가 있다. Review 모드는 관리자 승인 후 실행하고, Autonomous 모드는 바로 실행한다. 도구별로 allow/ask/deny를 정하고, agent hooks로 거버넌스 체크포인트를 둔다.
- PagerDuty는 에이전트가 추천 조치를 실행할지, 승인을 기다릴지를 사용자가 정한다.
- Rootly는 모든 변경에 명시적 사람 승인을 받는다. incident.io는 "엔지니어가 최종 결정"이라고 밝힌다. New Relic은 롤백 같은 제안을 엔지니어가 검토하도록 한다. Komodor도 조치 선택을 사람에게 맡긴다.
- Splunk는 아예 실행하지 않는다. 사용자가 kubectl 명령을 직접 돌리고 출력을 다시 넣는 구조다. Google은 읽기 전용 OAuth 토큰을 쓰고 데이터를 수정하지 않는다고 명시한다. Traversal은 "읽기 전용 접근부터 시작하라"고 권한다.
- **우리 프로젝트와의 연결**: 우리 에이전트는 런북을 골라 온콜 엔지니어에게 답하는 데까지만 하고, 실행은 사람이 한다. 이 설계는 업계 기본값(Review 모드)과 같다. 트레이드오프 절에서 "자율 실행을 넣지 않은 이유"의 근거로 쓸 수 있다.
- 근거 출처: Azure 개요 문서, PagerDuty Spring 26 블로그, Rootly AI SRE 페이지, incident.io 블로그, New Relic 문서, Splunk 기능 문서, Google 조사 문서, Traversal 가이드

### 인사이트 5. LLM 비용은 이미 과금 단위가 됐고, 소형, 대형 모델 2단 구성이 상용 제품에 들어가 있다. 우리 캐스케이드와 같은 발상이다

- ServiceNow AIOps LEAP 3.1.2(2026-03)는 **Small 트랙(GPT-4o mini 등)과 Large 트랙(GPT-4o 등)**을 나눠 제공한다. 우리 캐스케이드(gpt-4o-mini → gpt-4o)와 모델 조합까지 같다. 다만 ServiceNow 문서에는 "실패 시 상위 모델로 승격" 같은 캐스케이드 로직이 명시돼 있지 않다. 트랙 선택 방식으로 보이며, 이 부분은 확인하지 못했다.
- Datadog은 조사 1회에 약 6.5 AI credits를 쓴다고 공개했다. 크레딧은 연간 약정 시 $500/500 credits/월, 온디맨드는 $1.30/credit다. 온디맨드 기준 조사 1회는 약 $8.45다(6.5 × 1.30, **필자 계산**).
- Azure SRE Agent는 Azure Agent Units(AAU) 사용량으로 과금한다. AWS는 Support 지출에 비례하는 크레딧을 준다. Dynatrace는 결정론적 에이전트를 결합해 "절반 비용"을 얻었다고 주장한다(벤더 주장).
- **우리 프로젝트와의 연결**: 조사 1회 비용은 이미 고객 청구서에 찍히는 항목이다. 그래서 캐스케이드로 "품질 유지 + 호출 비용 절감"을 수치로 보이는 것은 실무적 의미가 있다. Ablation 표에 "건당 비용(토큰, 달러)" 열을 두면 업계 과금 단위와 바로 비교할 수 있다.
- 근거 출처: ServiceNow AIOps LEAP 릴리스 노트, Datadog 가격 페이지, AZ569760, Azure 문서, AWS GA 공지, Dynatrace 보도자료

### 인사이트 6. MCP가 사실상 표준 연동 규격이 됐다. 외부 도구가 늘수록 도구 장애 내성이 중요해진다

- MCP 지원 현황:
  - PagerDuty MCP 서버 GA(2025-10), SRE Agent 커넥터의 MCP 추가 GA(2026-06)
  - Datadog MCP 서버 GA(2026-03-09)
  - Rootly MCP GA(2026-03-12)
  - incident.io 원격 MCP Public Beta(2026-03-31)
  - Azure SRE Agent의 MCP 커넥터
  - AWS DevOps Agent의 MCP/ACP/A2A 지원
  - Grafana Cloud MCP 서버
- 한 에이전트가 MCP로 경쟁사 관측 도구를 끌어다 쓰는 구조가 흔하다(Azure→Datadog, Splunk, New Relic, Dynatrace, PagerDuty→Splunk, Datadog, Dynatrace).
- **우리 프로젝트와의 연결**: 베이스 에이전트도 research 단계에서 MCP 도구를 호출한다. 실무 환경에서는 커넥터가 20개 이상으로 늘어나므로, 일부 도구가 실패해도 답을 내는 장애 내성과 비동기 I/O 병렬 호출이 실무 요구와 맞닿는다. 다만 상용 제품이 도구 장애 시 어떻게 동작하는지는 공개 자료에서 찾지 못했다. 이 부분은 근거 없는 주장으로 쓰지 말 것.
- 근거 출처: PagerDuty 릴리스 노트, Datadog MCP GA 보도자료(Nasdaq 게재본), Rootly, incident.io 체인지로그, Azure 개요 문서, AWS 문서, Grafana GA 공지

### 인사이트 7. "LLM 단독"보다 "결정론적 장치 + LLM" 혼합이 업계 흐름이다. 규칙 기반 Validator를 버리지 않고 Judge를 얹는 설계의 근거가 된다

- Dynatrace는 결정론적 인과 AI(Smartscape 의존성 그래프)와 에이전트를 결합했다. New Relic은 토폴로지 그래프와 확률적 인과 모델로 원인 후보를 좁힌 뒤 생성형 모델을 쓴다. ServiceNow는 서드파티 관측 에이전트 결과를 워크플로로 묶는다.
- Datadog은 모든 도구 출력을 한 프롬프트에 몰아 요약하던 초기 설계에서 무관한 신호에 모델이 흔들렸다고 밝혔다. 그래서 가설 단위로 범위를 좁히는 구조로 바꿨다.
- **우리 프로젝트와의 연결**: 베이스의 규칙 기반 Validator를 값싼 1차 게이트로 두고, LLM-as-a-Judge를 품질 판정으로 추가하는 구성은 이 혼합 흐름과 맞는다. Analysis 노드의 게이트로 무관한 근거를 걸러 내는 설계도 Datadog의 교훈과 같은 방향이다. Ablation으로 "규칙만 / Judge만 / 둘 다"를 비교하면 이 주장을 우리 데이터로 검증할 수 있다.
- 근거 출처: Dynatrace 보도자료, New Relic 보도자료, ServiceNow 릴리스 노트, Datadog 구축기 블로그
