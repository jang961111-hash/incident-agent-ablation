# 평가 설계

## 평가셋

`eval/queries.yaml`. 총 24건 목표.

| 카테고리 | 건수 | 보는 것 |
|---|---|---|
| normal | 12 | 런북 6종 x 2건. 정상 경로 품질 |
| constrained | 3 | 길이·형식 제약 준수 (명확성) |
| composite | 3 | 복합 장애. 런북 2건 이상 필요 |
| unregistered | 3 | 미등록 시스템. 추측하지 않는지 |
| ambiguous | 3 | 모호한 요청. 되묻는지 |

**고정 원칙**: 한 번 라벨링한 평가셋은 구성이 바뀌어도 수정하지 않는다.
수정하면 Before/After 비교가 무의미해진다. 바꿔야 하면 version을 올리고 전 구성을 재실행한다.

## 지표 정의

### 답변 품질 — LLM-as-a-Judge

| 지표 | 보는 관계 | Pass 조건 |
|---|---|---|
| Relevance | Query ↔ Answer | 질문이 묻는 것에 답했다 |
| Completeness | Answer ↔ Context | Context의 필수 정보가 들어갔고, 없는 수치를 만들지 않았다 |
| Domain Appropriateness | Answer ↔ Context | Context의 도메인 조치·절차가 반영됐다 |
| Clarity | Answer 단독 | 논리적·체계적으로 작성됐다 |

4지표 중 통과 비율이 임계치 75% 미만이면 재작성. 즉 3개 이상 Pass해야 통과. (v1의 80%는 4/4만 통과시키는 오류라 0.75로 고침)

### 검색 품질

- `Recall@k` — 정답 런북이 상위 k건에 포함된 비율. 복합 장애는 정답이 2건이므로 부분 점수.
- `MRR` — 첫 정답의 역순위. 정답을 1위로 올렸는지 본다.

base 구성(키워드 규칙)도 선택한 런북을 기록하므로 동일 지표로 비교된다.

### 운영

p50/p95 지연, prompt/completion 토큰, 추정 비용, 재작성 횟수.
비용은 단가표 기반 **추정**이며 보고서에 그렇게 표기한다.

### 평가자 검증

`human_label` 이 채워진 건에 대해 (사람 Pass/Fail) == (Judge 통과 여부) 일치율을 낸다.
base 구성 답변을 보고 라벨링한다. 라벨은 이후 수정하지 않는다.

## 측정 절차

```bash
python -m eval.run_ablation --config eval/configs/base.yaml   # Before
# ... 사람 라벨 입력 ...
python -m eval.run_ablation --all                             # 4구성
python -m eval.report --md                                    # 비교표
```

## 결과 보관

`results/{구성}_{YYYYMMDD_HHMM}.json` 에 전건 기록, `{구성}_latest.json` 이 리포트 입력.
원시 트레이스는 LangSmith에 남고 `trace_url` 로 연결한다.
